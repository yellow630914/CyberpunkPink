## 必修

### 必修 1：車上（活動 `ride`）的放行表沒有戰鬥與成人場景，車上的事件選「開打」或「進場景」整步被擋

- 檔案：`engine/src/features/transit/index.ts:82`（`allow: ['commit:transit.', 'commit:event.', 'event.start', 'chain:free_action', 'commit:npc.']`）；工單 `dev/work/M2-transit.md:14` 列的就是這張表，所以這是工單本身的漏洞。
- 規格出處：EVENTS 4.10 節交通範圍的表：「追兵上車」的選項有「車上開打（戰鬥，空間窄：雙方遮蔽一律暴露）」；「癡漢」「可能走進成人場景」。另外 EVENTS 4.10 末段寫「坐到目的地（快轉）時，這些事件照樣擲」。
- 失敗情境（實測）：
  1. `makeCityGame`，加一件 `scope: transit` 的事件，選項 `fight` 的結果是 `{ kind: 'fight', foes: [...] }`，另一個選項帶 `adult_scene`。
  2. 在塔下站 `board`、`wait`，事件在月台開起來（活動是 `event`＋`ride`）。
  3. `chooseOption(..., 'fight')`、`chooseOption(..., 'go')` 都丟 `ActionBlocked: 你在車上，要先下車才能做這件事。`。
  4. 事件視窗停在原地。`eventView` 照樣把這兩個選項列成可選，玩家按了才被擋，原因也是錯的：玩家根本下不了車，因為事件擋住了 `commit:transit.`。
- 原因：`event.close` 的 `launch`（`battle`／`scene`）在 `Game.launchIn` 問 `battle.start`／`scene.start`，`ride` 不放行，整步回滾（不變式第 84 條的行為本身沒錯）。就算放行 `battle.start`，戰鬥開打之後的每一步（`battle.`、`commit:battle.`、`chain:battle_end`、`battle.retry`），以及打輸之後的 `commit:defeat.`、`commit:capture.`，也都要 `ride` 放行。白名單是「每一個進行中的活動都要放行」。
- 要 architect 決定的：車上開打與進場景要怎麼處理。做法一是 `ride` 放行整組戰鬥、戰敗、場景的前綴。做法二是戰鬥或場景開始時把這一趟結束：人下車在下一站，`transit` 聽 `activity.end` 或開始的報告。後者比較接近「追不到月台」的寫法。另外，事件視窗列選項時最好能先問這個選項的 `launch` 放不放行，不然畫面上可選、按下去才擋。

## 應修

### 應修 1：副本的放行表有 `rewind:stage`、`rewind:entry`，沒打輸也能隨時回到階段開始或入口

- 檔案：`engine/src/features/commission/index.ts:47-49`（`COMMISSION_ALLOW` 的最後兩項）；`engine/src/shell/game.ts:583-589`（`rewindToKind` 只問 `blockOf('rewind:<種類>')`）。工單 `dev/work/M2-commission-run.md:33` 要求放行這兩項。
- 規格出處：COMBAT_SYSTEM 8.4 節（「回到這個階段開始時」是戰敗之後的三選一之一）；GAME_DESIGN 第 9 節第 158 行（回退以一次動作為單位，最多連續 5 步）；SERIES 第 6 節（出副本只有達成、撤退、全員倒下）。
- 失敗情境（實測）：
  1. `makeCommissionGame` → `go` → 打完第一階段 → 第二階段 `chooseFace('meat')`，此時 `step: 'branch'`，沒有戰鬥也沒有等著選的戰敗。
  2. `g.rewindToKind('stage', '回去')` 回傳 `null`，人回到第二階段選面之前，時間也回去了。
  3. 所以玩家可以在任何一步之後（例：潛行的分支擲失敗、看完遭遇的配置），不受 5 步的上限，直接回到階段開頭換一條路。
- 另一半：`rewindToKind('entry')` 等於不經過 `commission.retreat` 的撤退。不會發 `activity.end`（outcome `retreat`），fixer 沒有記下 `fixer.pend retreat`，所以 `rewind.keep` 不退請來的人與付出去的錢，和正式撤退的結果不一樣。
- 建議：把這兩個 `rewind:` 從 `COMMISSION_ALLOW` 拿掉。回到階段只走 `Game.rewindToStage`（它本來就只在等著選的戰敗時成立），撤退只走 `commission.retreat` 這份報告（帶 `rewind` 的報告不另問 `rewind:` 的放行；0016 實作補記已經這樣寫）。

### 應修 2：撤退之後再進去，骰子和上一趟一模一樣

- 檔案：`engine/src/shell/game.ts:800-807`（`restoreFrom` 用快照裡的 `rng`，只留 `seq`）。亂數會固定的擲骰有：
  - `engine/src/features/commission/run.ts:331`（分支的檢定 `commission/<委託>/<階段>/branch`）；
  - `engine/src/features/commission/aux.ts:202`（輔助面）；
  - `enemy_pick` 的 seed（`run.ts` 的 `foeRef`）。
- 規格出處：SERIES 第 6 節第 111 行：「重來時骰子不保證和上一次一樣：撤退放棄整趟進度本身就是代價，所以不像一般的回退那樣固定骰值（一般的回退照舊不換種子）」；GAME_DESIGN 第 9 節第 158 行同一句。
- 失敗情境（實測）：
  1. `makeCommissionGame` → `go` → 選現實面 → 選潛行分支，擲出 `commission.roll` 自然 15，`rng` 是 `{ seed: 6, cursor: 1 }`。
  2. `retreat` → 再 `go` → 同一條路，又是自然 15、同樣的 `rng`。
  3. 戰鬥裡的骰子會變（核心用 `battle/<戰鬥 id>/…`，而戰鬥 id 跟著不回退的 `seq` 走），但分支的檢定、輔助面、挑到的敵人都不變。
- 要 architect 決定：撤退（`rewind: entry` 那一份）回去之後換種子或推進游標。例：`restoreFrom` 收一個參數，讓撤退的那一條路把 `next.rng` 換成 `current.rng` 再往前推一格。一般的回退與回到階段維持固定。戰敗接受之後的委託失敗也回到 `entry`，設計書沒有明說，一起定。

## 建議

### 建議 1：會影響抽籤順序的排序用了 `localeCompare`

- 檔案：
  - `engine/src/features/fixer/gen.ts:531`（連動依 id 排序之後再用衍生亂數抽）；
  - `engine/src/features/enemies/capture.ts:125`（俘虜依單位 id 排序之後每人抽一次）；
  - `engine/src/features/world/index.ts:101`。
- 規格出處：EVENTS 3.2 節「所有亂數用存檔種子＋時間＋觸發點，回退之後重來會得到同樣的結果」；不變式第 5、112 條（同一個種子結果一樣）。
- 失敗情境：`localeCompare` 不帶語系時用執行環境的語系。介面在瀏覽器裡跑，捷克、斯洛伐克語系會把 `ch` 排在 `h` 後面，立陶宛語系有其他特例。同一份存檔在兩台機器上生成的委託連動、俘虜結果可能不同。測試在 node 的預設語系下看不到。
- 建議：改成依 code point 比（`a < b ? -1 : a > b ? 1 : 0`）。

### 建議 2：不變式第 107 條的掃描認不得 enemies 的 `capture` 鍵

- 檔案：`engine/src/features/enemies/capture.ts:26`（`export const CAPTURE_KEY = 'capture'`）；`engine/src/testkit/layers.ts` 照「名字帶 `EXT` 的常數」認誰擁有哪個鍵。
- 失敗情境：別的功能寫 `state.ext.capture`，掃描不會報。
- 建議：改名成 `CAPTURE_EXT`，或讓掃描也認 `*_KEY`。

### 建議 3：名冊「忠誠 20 以下離開」的邊界是 `<= 20`，和設計書另一列重疊

- 檔案：`engine/src/features/roster/ops.ts:201`（`loyalty <= rules.leave_at`，`leave_at` 是 20）。
- 規格出處：NPC_SYSTEM 10.4 節的表同時有「20～39：出場費 +25%」與「20 以下：每週 30% 離開」，20 兩列都算得進去。
- 現在的程式讓忠誠剛好 20 的人同時漲出場費又可能離開。設計書要定一個邊界（建議「20 以下」改成「低於 20」）。
