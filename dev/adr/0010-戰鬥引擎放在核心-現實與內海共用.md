# 0010 戰鬥引擎放在核心，現實與內海共用；規則是資料、行動是登錄表

- 日期：2026-11-22　狀態：採用（M1 開工；MIGRATION 第 5 節「現實與內海是同一套戰鬥、同一個地圖引擎」）

## 背景
第四版的 Demo（`ui/src/lib/combat/`）有三份戰鬥：`real.ts`、`net.ts`、`opinion.ts`，共用一份 `field.ts`（站位與遮蔽）。現實與內海的規則九成一樣（四格縱深、遮蔽、行動點、命中、感載與過載、敵人的 AI），差的是：內海沒有生命、過載是閃斷、遮蔽叫防火牆、餘韻的效果相反、防護對感載有效。Demo 的做法是各寫一份，規則改一處就要改兩處，而且已經不一致（這一批逐條對照 COMBAT_SYSTEM 找到的出入，見 0013）。
M1 只做現實戰鬥，但 M3 的內海要接得上；M1 之內就有六七個功能要動到戰鬥（行動表、敵人、裝備、技能、無人機、戰敗、探索），功能之間不能互相 import。

## 選項
1. **戰鬥是一個 L6 的功能**（`features/combat`），內海另一個功能，兩邊各自一份引擎。照搬 Demo，最快；但兩份規則會分岔，技能、裝備、敵人這些功能要用到戰鬥的型別與基本動作時只能 import 另一個功能（違反分層），或把一切塞進掛鉤的 payload。
2. **引擎在核心，戰場的差別寫在程式的分支裡**（`if (mode === 'net')`）。一份規則，但每多一個戰場就多一層分支，數字改一個要改程式。
3. **引擎在核心，戰場的差別是資料；有哪些行動、每個行動做什麼是登錄表**。核心只有機制；現實的行動表、內海的行動表、技能、敵人各是一個功能，往登錄表註冊。

## 決定
採用 3。

- **`engine/src/core/battle/`（L5）是引擎**：站位與距離、遮蔽與補位、回合與行動點、命中與要害、傷害類型與護甲、感載、過載與餘韻、狀態、監視、後方的增援、和人重疊的東西、機體的接口、敵人 AI 的骨架（挑目標、位置分、替行動打分、平方加權抽）、開打與結束。型別在 `core/types/battle.ts`（L0）。
- **戰場是資料**（內容種類 `battle_mode`）：有哪幾條軌、過載是失去回合還是閃斷、餘韻對檢定與感載的效果、防護對不對感載有效、遮蔽叫什麼，以及一整組數字（`BattleNumbers`：每回合回幾點、迴避的基礎、要害的門檻、距離的懲罰、遮蔽的加值與耐久、消退、制伏與脫離的 DC……）。傷害類型（`damage_type`）、戰鬥中的狀態（`battle_status`）、武器的類型（`weapon_class`）也是資料。核心帶著照設計書寫的預設值（現實與內海各一份），資料逐項寫出來之後蓋掉；沒有資料時核心的測試照樣跑。
- **行動是登錄表**（`k.battle.action`）：核心只有每個戰場都一樣的兩個（結束回合、換位）。現實的行動表由 `features/combat` 註冊，內海的（M3）由它自己的功能註冊，技能把每個主動技能註冊成一個行動。每個行動自己回答：誰有、花多少、現在為什麼不能做（一條一條的句子）、可以選哪些目標與各自選不了的原因、做什麼、AI 給它幾分。
- **其餘的接點也是登錄表**：掛點（單位組好、開打、回合開始與結束、擲命中之前與之後、重創、過載、退出、換位、站上暴露的格子、機體歸零、被擊落、AI 的每一步之前、分出結果）、修正（`k.battle.modifier`：命中、迴避、傷害骰、穿甲、要害門檻、先攻、每回合回的點數、行動的花費……）、戰鬥結束時加進報告的變更（`onEnd`）、「誰上場」的來源（`unitSource`：核心有角色與直接給的單位，敵人的功能註冊 `enemy`）、角色帶進戰鬥的裝備（`loadout`）、道具在戰鬥裡的效果（`itemOp`）。
- **功能改戰鬥狀態只用 `BattleRun` 的基本動作**（攻擊、傷害、灌感載、治療、給狀態、推拉、換位、動遮蔽、讓人退出、分出結果……）。行動與掛點拿到的是這一步的工作副本，不碰 `GameState`。
- **事件是封閉清單**（`BATTLE_EVENTS`）：每一拍紀錄帶著事件的標籤與數字（要害、過載、打倒、制伏、重創、遮蔽被打穿……）。直播的容器（M5）、紀錄、之後的功能聽這些，不解析文字。
- **機甲留到 M6**：核心只有接口——單位可以掛一個機體（`BattleHull`：耐久、護甲、回灌的比例、剩幾回合），受傷先扣機體、照比例回灌感載、歸零時呼叫掛點。
- **測試基礎建設**帶一組最小的行動（`TEST_COMBAT`：攻擊、換彈、監視）與具名的情境（一般遭遇、精英遭遇、首領戰、要活的、打不贏的），核心的測試、冒煙、探針不必等功能做完。

## 後果
- 規則只有一份。內海在 M3 要做的是：一筆 `battle_mode`（核心已經有預設）、它自己的行動表與構裝、蕾絲的單位來源；引擎不用再寫。
- 核心變大了（戰鬥約兩千行）。分層檢查把 `core/battle` 算在 L5；它不 import 任何功能。
- 行動表在功能裡，所以「只有這張表上的行動」（COMBAT_SYSTEM 1.3 節）要靠功能的驗收測試守住，核心不擋別的功能多註冊行動。
- 數字是資料，世界編輯器之後可以改；但一場戰鬥的平衡是這一整組數字一起決定的，改資料要跟著跑平衡模擬。核心的預設值與資料不一致時以資料為準，`M1-data-rules` 的驗收測試比對兩邊。
- Demo 的三份戰鬥（`ui/src/lib/combat/`）在介面換成引擎之後才刪：現實的在 `M1-ui-combat` 之後，內海與輿論的等 M3、M5。
