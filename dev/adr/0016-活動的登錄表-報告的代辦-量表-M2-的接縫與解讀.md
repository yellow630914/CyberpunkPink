# 0016 活動的登錄表（開始、擋住別的事、結束交回）；報告的代辦；量表；事件導演與名冊的接縫；時間與花費；M2 的解讀與暫定值

- 日期：2026-11-23　狀態：設計（M2 開工；核心的部分由四張工單實作：dev/work/M2-core-activity.md、M2-core-shell.md、M2-core-meters.md、M2-core-battle.md，派 cpp-architect 角色、指定 sonnet；第八節的解讀與暫定值等使用者看）
- 延續 0010（引擎在核心、行動是登錄表）、0011（快照在狀態裡）、0012（格子地圖）、0014（等著選的戰敗由核心擋）、0015（效果是登錄表）。

## 背景

M2 一次搬十幾個功能（MIGRATION 第 6 節）：委託副本、事件導演、城市地圖與交通、NPC 與關係、名冊、交易、敵對值與掃橋、每週帳單、打工、橋參數、最小的住處、成人場景的最小版。逐條對過之後，它們互相要用到的東西只有五類，現在的核心都還沒有：

1. **誰開誰的東西**。事件的結果開一場戰鬥或一場成人場景；戰敗開一件戰敗事件；副本的一個階段開一張地圖；掃橋跳出一個要選的框。現在只有「走到一格就開打」寫死在 `GridEffect.battle` 與 `Game.gridMove` 裡。
2. **誰擋住誰**。`Game.blockOf` 只認戰鬥與等著選的戰敗（0014 最後一條留了話）。M2 多了：副本是封閉的、擋住行動的事件要先回應、場景進行中。
3. **做完之後交回給誰**。副本的階段要知道那一場打完了、那一場場景的目的達成了沒有；之後內海（M3）、輿論戰（M5）也是「副本的階段開一段別的玩法，做完交回來」。
4. **別的功能的數字**。敵對值、好感、親密度、忠誠、豔名、街頭信譽、警戒：事件要加減、條件要看、交易要拿來算價錢、副本要拿來算警戒的起始值。功能之間不能 import，也不該讀別人的 `state.ext`。
5. **要外殼才做得到的事**。存快照（要存檔的文字）、回到快照（撤退、委託失敗）、寫正文（任務鏈）。功能在 L6，碰不到 L7。

## 選項

1. 照 0010 的做法把導演、副本、場景都放進核心。核心會變成整個遊戲；而且這三個都不像戰鬥那樣有六七個功能要往裡面註冊行動。
2. 每個功能開自己的掛點（照 `defeat.options` 的做法，用 `declare module` 補型別）。做得出來，但「開始、擋住、交回」每一對功能各寫一次，介面與外殼的入口也跟著一個功能一個。
3. **核心加四個小機制，其餘都是 L6**：活動的登錄表；報告上的代辦；量表；報告上的觸發點。功能對功能的掛點只留「一方問、多方答」的那幾個（第七節的表）。

## 決定

採用 3。

### 一、活動（`k.activity`，L5；工單 M2-core-activity）

**活動**是一段獨佔的、要玩家一步一步做完的過程：戰鬥、等著選的戰敗、事件視窗、成人場景、委託副本，之後的子網與輿論戰。每一種登記三件事：怎麼開始、進行中放行什麼、（結束時）交回給發起的人。

```ts
interface Origin { by: string; ref?: string; ext?: Record<string, unknown> }   // 誰發起的；ext 的慣用鍵見第五節
interface Launch { kind: string; setup: unknown; origin?: Origin }
interface ActivityDef {
  kind: string; owner: string
  order: number                                         // 小的先問（越內層越小）：battle 0、defeat 10、scene 20、event 30、commission 90
  active(state): { id: string; label: string } | null   // 進行中嗎：讀自己的狀態
  allow: string[]                                       // 進行中放行的 doing 前綴
  allows?(state, doing, draft?): boolean                // 前綴之外的特例（戰敗：帶 snapshot.drop 的報告）
  reason(state, doing): string                          // 擋下時給玩家看的完整句子
  start?(k, state, setup, origin): ReportDraft[]        // 開始：純函式；開不成丟 ActionBlocked（一條一句）
}
```

- `k.activity.define(def)`、`k.activity.allow(kind, prefix, owner)`（別的功能把自己的 doing 加進某個活動的放行清單）、`k.activity.active(state)`、`k.activity.blockOf(state, doing, draft)`、`k.activity.start(k, state, kind, setup, origin)`。
- **放行是白名單**：進行中的每一個活動照 `order` 都要放行，第一個不放行的給原因。新功能忘了登記，結果是「在副本裡用不了」，測試看得到；反過來做（黑名單）忘了登記就是漏洞。
- `doing` 的寫法沿用 0014：`chain:<鏈的 id>`、`commit:<報告的 action>`、`<kind>.start`、`battle.retry`、`rewind:<快照的種類>`、`grid.enter`、`grid.move`。**報告的 `action` 一律是「功能的前綴.動詞」**（`event.choose`、`commission.face`、`trade.checkout`），前綴在第七節的表。
- 戰鬥與等著選的戰敗改成核心內建的兩筆（行為、句子、不變式第 48、59 條都不變）；`Game.blockOf` 改問登錄表。
- **結束交回**：核心的掛點 `activity.end`，收到 `{ state, kind, id, origin, outcome, result }`，可以回傳 `{ changes?, lines?, launch?, rewind? }`。活動的主人在組「結束的那一份報告」時呼叫它，把回傳的東西併進那一份（`changes` 接在後面、`lines` 進結果、`launch` 與 `rewind` 放到報告上）。聽的人看 `origin.by` 是不是自己。核心的戰鬥結算也發（`kind: 'battle'`，`outcome` 是 win、lose、flee、surrender；原本的 `k.battle.onEnd` 照舊）。
- `GridEffect` 多 `launch?: Launch[]` 與 `triggers?`（原本的 `battle` 留著，等於 `launch` 一場戰鬥）。

### 二、報告上的代辦（工單 M2-core-activity、M2-core-shell）

功能只會交報告。要外殼做的事寫在報告上，外殼在提交之後照做：

| 欄位 | 意思 | 外殼做什麼 |
|---|---|---|
| `launch?: Launch[]` | 這份報告提交之後接著開的活動 | 照順序 `k.activity.start` 再提交（戰鬥走原本的 `startBattle`，含開打前的快照）。**開不成，整步不成立**：狀態回到這一步之前，丟 `ActionBlocked`（和 0014 的「戰開不起來整步不走」同一條）。最多連開四層 |
| `rewind?: { kind, summary }` | 提交之後回到最近一份這個種類的快照 | `Game.rewindToKind`：紀錄留著並標成被收回、`rewind.keep` 掛點照舊。撤退與委託失敗都是一份帶 `rewind` 的報告，介面不直接呼叫回退 |
| `triggers?: Array<{ point, where? }>` | 這一回合碰到的觸發點（EVENTS 3.1 的名字） | 外殼不做事；事件導演在 `turn.end` 讀它 |
| `adult?: boolean` | 這一份是成人場景（GAME_DESIGN 第 9 節的 `adult_scene` 記號） | 寫正文時走成人路由，其餘規則不因它而不同 |

- **存快照是一筆變更**：`{ op: 'snapshot.take', kind, label, owner?, data?, replace? }`，一定是那份報告的第一筆；存的是「這份報告套用之前」的狀態，文字由外殼注入核心的 `k.serialize` 產生。`replace` 是同一個 `owner` 同一種只留最新一份（階段）。原本的 `snapshot.add`（自己帶文字）留著。
- **結算之後寫正文**：`Game.commitNarrated(draft, { mode, label? })` 跑一條通用的鏈（給定的草稿 → `narrate` → 套用）；AI 關著就等於 `commit`。M2 的移動、交易、休息、事件、打工、副本的階段、場景的結束都走它，不各開一條鏈。要 judge 的（NPC 互動、事件的「我要做別的」）走現有的 `free_action`。

### 三、量表（`state.meters`，L3；效果與條件自動有，L4；工單 M2-core-meters）

CORE_RULES 第 8 節的「名聲與敵對值」加上個人的親密度與忠誠，都是同一種東西：**一個有範圍的數字，照對象分開記，事件可以加減、條件可以看**。做成核心的一張表（MIGRATION 第 5 節第 4 條：敵對值從一開始就照勢力記）。

```ts
k.meters.define({ kind, owner, name, min, max, start, keyed: 'faction' | 'npc' | 'district' | 'map' | 'none',
                  cap?: { down: number; up: number },   // AI 給的效果一件事合計的上限（EVENTS 2.4）
                  floor?: string,                       // 下限是另一張量表的值（敵對值的下限）
                  adjust?(state, key, delta): number }) // 效果進來時的修正（區的倍率）
state.meters[kind][key]                                  // 沒寫的就是 start
{ op: 'meter', kind, key, delta } | { op: 'meter', kind, key, set }
meterOf(k, state, kind, key?): number
```

- 定義一種量表，同名的**效果** `{ kind, key?, amount }`（和現有的 `cash`、`cred` 一樣用 `amount`） 與**條件** `{ kind, key?, min?, max? }` 就自動註冊（上限照 0007 的三級：內建照寫、AI 照 `cap`）。`key` 省略時照 `keyed`：`district` 是現在這一區、`map` 是現在這張地圖的實例、`none` 是 `_`。
- M2 的量表：

| kind | 主人 | 照什麼記 | 範圍 | 出處 |
|---|---|---|---|---|
| `hostility`、`hostility_floor`、`favor` | security | 勢力 | 0～100 | FACTIONS 第 6 節、CORE_RULES 第 8 節 |
| `affinity` | npcs | 人 | −100～100 | NPC_SYSTEM 第 7 節 |
| `loyalty` | roster | 人 | 0～100 | NPC_SYSTEM 10.4 |
| `fame` | lewd | 區 | 0～100 | LEWD_SYSTEM 第 5 節 |
| `rep` | fixer | 單一 | 0～100 | CORE_RULES 第 8 節；同時註冊衍生數值 `rep_grade` |
| `insight` | scene | 單一 | 0 起，沒有上限 | LEWD_SYSTEM 第 10 節 |
| `alert` | explore | 地圖的實例 | 0～100 | COMMISSIONS 2.3、SITES 12.5 |

- 沒有人定義的種類，`meterOf` 回傳 0（那個功能這一局沒裝）；所以交易算折扣、互動算 DC 時直接問量表，不必知道誰管它。
- **規矩**：功能讀別人的數字只經由 `meterOf`、`k.stats`、`k.conditions`、內容（`k.content`）與核心的狀態（`party`、`actors`、`maps`、`money`）；寫只經由變更與效果。**不讀別的功能的 `state.ext`。** 人身上的狀況（有空、受傷、躲風頭、被捕、在忙）用核心的 `actor.conditions`，id 是共用的字彙：`busy`、`injured`、`lying_low`、`arrested`。
- 存檔升到第 3 版（多 `meters`；第 2 版的讀進來是空的表）。

### 四、事件導演是功能；事件視窗是通用的執行器（工單 M2-director、M2-event-run）

- 導演（`features/director`）在 `turn.end` 讀這一回合的 `report.triggers`，照 EVENTS 第 3 節擲；`daily`、`weekly` 聽 `time.passed`。發觸發點的功能只在自己的報告上寫 `triggers`，不知道導演存在。
- **事件視窗是活動 `event`**：`setup` 是 `{ event: id }` 或 `{ inline: 一件事件 }`。它管選項、看不看得到、檢定、四級結果、多段與版本（戰敗事件就是這個格式）。別的功能要玩家「在幾個選項裡選一個、可能擲一次骰」時都交給它：掃橋的怎麼過、俘虜的處置、雇主問要不要升階、戰敗事件。做完從 `activity.end` 拿到 `{ event, option, degree, flags }`。
- 結果分兩種：**改狀態的是效果**（`k.effects`，由管那塊狀態的功能註冊）；**開活動的是指示**（`fight`、`chain`、選項上的 `adult_scene`），執行器把它們變成 `launch`。沒有人登記 `scene` 這種活動時，`adult_scene` 當成沒有（退路）。
- 事件資料的效果一律寫物件 `{ kind, ... }`。EVENTS 第 7 節、DATA 第 4 節樣本裡的陣列寫法（`["cash", 300]`）是文件的簡寫，匯入時轉；引擎不收。

### 五、名冊的人進戰鬥；開打前帶進去的東西（工單 M2-core-battle、M2-roster、M2-abilities-m2）

- **隊伍就是核心的 `state.party`**（含主角最多 4 人）；探索開戰時我方照它排。同行（最多 2 位）不上場，是名冊自己的資料。
- **候補**：`k.battle.bench(owner, fn)` 回答「這一方現在叫得到誰」（每個人一筆 `{ id, ref, name, blocks }`）；`run.callIn(side, ref)` 把他排進後方的最前面、下一輪開頭補進最後面的空格（補位照 0013 C6），沒有空格回傳 `null`、不動狀態。名冊註冊候補（名冊上不在隊上、身上沒有 `busy`、`injured`、`lying_low`、`arrested` 的人）；技能的「增援」只呼叫 `callIn`，不知道名冊。
- **開戰設定的慣用鍵**（`BattleSetup.origin.ext`，誰發起誰填）：`by`、`commission`（0015 E3 的那個鍵）、`stage`、`face`、`pre: { spotted?, disguise? }`（開打前被識破了沒有）、`defeat_event`（副本自訂的戰敗事件）。
- `BattleSetup.edge?: 'ally' | 'foe'`：那一方每個人的先攻擲兩次取高（G7）。
- 敵人的來源多 `enemy_pick`（照勢力、等級、位階挑一個兵種），`enemy` 與 `enemy_pick` 的 `UnitRef` 可以寫 `attached` 蓋掉兵種自己的（詞條「獵犬」；工單 M2-enemy-encounter）。

### 六、時間與花費

| 做什麼 | 花多久 | 誰加 `time` |
|---|---|---|
| 在城市的街區走一格 | G8（暫定 1 分鐘，鏽帶 2） | world |
| 搭車 | 每站照 DISTRICTS 1.2.1 的表，加等車 | transit |
| 在委託的地圖上走、戰鬥、事件視窗、成人場景 | 0（0013 C5 照舊） | — |
| 副本的一個階段做完 | 120 分鐘（COMMISSIONS 6.2） | commission，在里程碑那一份 |
| 踩點一次 | 一個時段 | fixer |
| 喘口氣、睡一覺 | 60、480 分鐘（DOWNTIME 第 2 節） | rest |
| 打工一班 | 120／240／480 分鐘 | work |
| 換技能配置 | 衍生數值 `loadout_minutes`（G1） | abilities |

- **錢付不出來就是做不成**（原因一句），不會扣成負的；帳戶與現金哪一種照各功能的規則。
- **跨過時間點的事**都聽 `time.passed`，照固定的順序：帳單 10、敵對值的消退 12、名冊的每週 14、NPC 自己的日子 16、導演的 `daily` 與 `weekly` 20。核心給 `crossings(from, to, { every, offset })`（L1）算跨過了幾個點：每週是週一 06:00（DOWNTIME 5.1），每天是 08:00（EVENTS 3.1）。
- **休息做完**發核心的掛點 `rest.done`（`{ state, kind: 'breath' | 'sleep' | 'stage' }`，回傳變更）：「每次休息回滿」的東西聽它；副本裡階段之間的喘口氣也發（`stage`）。

### 七、M2 的接縫一覽

**報告的前綴**（`commit:<前綴>.<動詞>`）：`world`、`transit`、`grid`（探索，沿用）、`event`、`scan`、`scene`、`defeat`、`capture`、`commission`、`fixer`、`roster`、`favor`、`npc`、`security`、`trade`、`bill`、`rest`、`home`、`work`、`lewd`、`ability`（沿用）、`gear`（沿用）。

**功能對功能的掛點**（一方問、多方答；宣告的那一方用 `declare module` 補型別，照 `defeat.options` 的做法）：

| 掛點 | 誰宣告、誰問 | 誰答 | 問什麼 |
|---|---|---|---|
| `activity.end`、`rest.done` | 核心 | 發起的功能；有「每次休息」的功能 | 第一、六節 |
| `director.cast` | director | npcs | 這個登場角色是誰（回傳角色的 id 與要先套的變更） |
| `scan.carried` | security | gear | 身上會被這一級掃到的東西 |
| `bill.collect`、`bill.settled` | bills | housing、roster（之後義體、店面……） | 這一週要收要付什麼；哪幾筆沒付成 |
| `defeat.options` | defeat（已經有） | abilities | 戰敗多出來的選項 |
| `fixer.offers` | fixer | 委託的生成（M2-commission-gen）；之後的特殊任務 | 這個中間人今天有哪些委託 |

**共用的資料慣例**（不 import，只認格式）：地圖實例的 `ext.guards`、`ext.reinforce`、`ext.origin`（探索讀，開地圖的人填）；`actor.ext.paths`（路數與階數，DATA 第 8 節）；`actor.ext.bridge`、`actor.ext.tendency`（DATA 第 8 節，lewd 管）。

## 後果

- 之後每一種新的玩法（子網、輿論戰、機甲整備的試車）是登記一種活動：副本的階段照 `face` 開它、等 `activity.end`，副本的程式不用改。M2 只登記現實面；沒有登記的面，玩家選不了，但輔助面照樣擲得了（那只是一次擲骰）。
- 外殼不再替每個功能加入口：介面的 store 直接呼叫功能匯出的純函式拿報告、交給 `Game.commit` 或 `Game.commitNarrated`；戰鬥原本的入口留著。
- 量表是核心的狀態，所以「這個勢力的敵對值」不必等 security 裝上才有地方放；但分段的效果、消退、區的倍率還是 security 的事。沒有人定義的量表種類，變更會被擋下（訊息寫出是哪一種）。
- 白名單的代價：副本裡能做的事要一個一個登記。清單在 M2-commission-run 的驗收條件裡守著。
- `snapshot.take` 讓快照變成資料的一部分，但文字要外殼給；只有核心、沒有外殼的測試由 testkit 給一個簡單的序列化函式。
- 事件執行器變成很多功能共用的東西：它的格式一動，掃橋、俘虜、戰敗、升階都要跟著看。格式以 M2-event-run 為準。
- 第八節被否決時要改的地方都只在一張工單的範圍裡；G1、G5、G6 動到的最多，先問。
