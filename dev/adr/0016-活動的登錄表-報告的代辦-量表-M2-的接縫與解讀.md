# 0016 活動的登錄表（開始、擋住別的事、結束交回）；報告的代辦；量表；事件導演與名冊的接縫；時間與花費；M2 的解讀與暫定值

- 日期：2026-11-23　狀態：設計（M2 開工；核心的部分由四張工單實作：dev/work/M2-core-activity.md、M2-core-shell.md、M2-core-meters.md、M2-core-battle.md，派 cpp-architect 角色、指定 sonnet；第八節的解讀與暫定值等使用者看）
- 延續 0010（引擎在核心、行動是登錄表）、0011（快照在狀態裡）、0012（格子地圖）、0014（等著選的戰敗由核心擋）、0015（效果是登錄表）。

## 背景

M2 一次搬十幾個功能（MIGRATION 第 6 節）：委託副本、事件導演、城市地圖與交通、NPC 與關係、名冊、交易、敵對值與掃橋、每週帳單、打工、橋參數、最小的住處、成人場景的最小版。逐條對過之後，它們互相要用到的東西只有五類，現在的核心都還沒有：

1. **誰開誰的東西**。事件的結果開一場戰鬥或一場成人場景；戰敗開一件戰敗事件；副本的一個階段開一張地圖；掃橋跳出一個要選的框。現在只有「走到一格就開打」寫死在 `GridEffect.battle` 與 `Game.gridMove` 裡。
2. **誰擋住誰**。`Game.blockOf` 只認戰鬥與等著選的戰敗（0014 最後一條留了話）。M2 多了：副本是封閉的、擋住行動的事件要先回應、場景進行中。
3. **做完之後交回給誰**。副本的階段要知道那一場打完了、那一場場景的目的達成了沒有；之後內海（M3）、輿論戰（M5）也是「副本的階段開一段別的玩法，做完交回來」。
4. **別的功能的數字**。敵對值、好感、親密度、忠誠、豔名、街頭信譽、警戒：事件要加減、條件要看、交易要拿來算價錢、副本要拿來算警戒的起始值。功能之間不能 import，也不該讀別人的 `state.ext`。
5. **要外殼才做得到的事**。存快照（要存檔的文字）、回到快照（撤退、委託失敗）、寫正文（任務鏈）。功能在 L6，碰不到 L7。

## 選項

1. 照 0010 的做法把導演、副本、場景都放進核心。核心會變成整個遊戲；而且這三個都不像戰鬥那樣有六七個功能要往裡面註冊行動。
2. 每個功能開自己的掛點（照 `defeat.options` 的做法，用 `declare module` 補型別）。做得出來，但「開始、擋住、交回」每一對功能各寫一次，介面與外殼的入口也跟著一個功能一個。
3. **核心加四個小機制，其餘都是 L6**：活動的登錄表；報告上的代辦；量表；報告上的觸發點。功能對功能的掛點只留「一方問、多方答」的那幾個（第七節的表）。

## 決定

採用 3。

### 一、活動（`k.activity`，L5；工單 M2-core-activity）

**活動**是一段獨佔的、要玩家一步一步做完的過程：戰鬥、等著選的戰敗、事件視窗、成人場景、委託副本，之後的子網與輿論戰。每一種登記三件事：怎麼開始、進行中放行什麼、（結束時）交回給發起的人。

```ts
interface Origin { by: string; ref?: string; ext?: Record<string, unknown> }   // 誰發起的；ext 的慣用鍵見第五節
interface Launch { kind: string; setup: unknown; origin?: Origin }
interface ActivityDef {
  kind: string; owner: string
  order: number                                         // 小的先問（越內層越小）：battle 0、defeat 10、scene 20、event 30、commission 90
  active(state): { id: string; label: string } | null   // 進行中嗎：讀自己的狀態
  allow: string[]                                       // 進行中放行的 doing 前綴
  allows?(state, doing, draft?): boolean                // 前綴之外的特例（戰敗：帶 snapshot.drop 的報告）
  reason(state, doing): string                          // 擋下時給玩家看的完整句子
  start?(k, state, setup, origin): ReportDraft[]        // 開始：純函式；開不成丟 ActionBlocked（一條一句）
}
```

- `k.activity.define(def)`、`k.activity.allow(kind, prefix, owner)`（別的功能把自己的 doing 加進某個活動的放行清單）、`k.activity.active(state)`、`k.activity.blockOf(state, doing, draft)`、`k.activity.start(k, state, kind, setup, origin)`。
- **放行是白名單**：進行中的每一個活動照 `order` 都要放行，第一個不放行的給原因。新功能忘了登記，結果是「在副本裡用不了」，測試看得到；反過來做（黑名單）忘了登記就是漏洞。
- `doing` 的寫法沿用 0014：`chain:<鏈的 id>`、`commit:<報告的 action>`、`<kind>.start`、`battle.retry`、`rewind:<快照的種類>`、`grid.enter`、`grid.move`。**報告的 `action` 一律是「功能的前綴.動詞」**（`event.choose`、`commission.face`、`trade.checkout`），前綴在第七節的表。
- 戰鬥與等著選的戰敗改成核心內建的兩筆（行為、句子、不變式第 48、59 條都不變）；`Game.blockOf` 改問登錄表。
- **結束交回**：核心的掛點 `activity.end`，收到 `{ state, kind, id, origin, outcome, result }`，可以回傳 `{ changes?, lines?, launch?, rewind? }`。活動的主人在組「結束的那一份報告」時呼叫它，把回傳的東西併進那一份（`changes` 接在後面、`lines` 進結果、`launch` 與 `rewind` 放到報告上）。聽的人看 `origin.by` 是不是自己。核心的戰鬥結算也發（`kind: 'battle'`，`outcome` 是 win、lose、flee、surrender；原本的 `k.battle.onEnd` 照舊）。
- `GridEffect` 多 `launch?: Launch[]` 與 `triggers?`（原本的 `battle` 留著，等於 `launch` 一場戰鬥）。

### 二、報告上的代辦（工單 M2-core-activity、M2-core-shell）

功能只會交報告。要外殼做的事寫在報告上，外殼在提交之後照做：

| 欄位 | 意思 | 外殼做什麼 |
|---|---|---|
| `launch?: Launch[]` | 這份報告提交之後接著開的活動 | 照順序 `k.activity.start` 再提交（戰鬥走原本的 `startBattle`，含開打前的快照）。**開不成，整步不成立**：狀態回到這一步之前，丟 `ActionBlocked`（和 0014 的「戰開不起來整步不走」同一條）。最多連開四層 |
| `rewind?: { kind, summary }` | 提交之後回到最近一份這個種類的快照 | `Game.rewindToKind`：紀錄留著並標成被收回、`rewind.keep` 掛點照舊。撤退與委託失敗都是一份帶 `rewind` 的報告，介面不直接呼叫回退 |
| `triggers?: Array<{ point, where? }>` | 這一回合碰到的觸發點（EVENTS 3.1 的名字） | 外殼不做事；事件導演在 `turn.end` 讀它 |
| `adult?: boolean` | 這一份是成人場景（GAME_DESIGN 第 9 節的 `adult_scene` 記號） | 寫正文時走成人路由，其餘規則不因它而不同 |

- **存快照是一筆變更**：`{ op: 'snapshot.take', kind, label, owner?, data?, replace? }`，一定是那份報告的第一筆；存的是「這份報告套用之前」的狀態，文字由外殼注入核心的 `k.serialize` 產生。`replace` 是同一個 `owner` 同一種只留最新一份（階段）。原本的 `snapshot.add`（自己帶文字）留著。
- **結算之後寫正文**：`Game.commitNarrated(draft, { mode, label? })` 跑一條通用的鏈（給定的草稿 → `narrate` → 套用）；AI 關著就等於 `commit`。M2 的移動、交易、休息、事件、打工、副本的階段、場景的結束都走它，不各開一條鏈。要 judge 的（NPC 互動、事件的「我要做別的」）走現有的 `free_action`。

### 三、量表（`state.meters`，L3；效果與條件自動有，L4；工單 M2-core-meters）

CORE_RULES 第 8 節的「名聲與敵對值」加上個人的親密度與忠誠，都是同一種東西：**一個有範圍的數字，照對象分開記，事件可以加減、條件可以看**。做成核心的一張表（MIGRATION 第 5 節第 4 條：敵對值從一開始就照勢力記）。

```ts
k.meters.define({ kind, owner, name, min, max, start, keyed: 'faction' | 'npc' | 'district' | 'map' | 'none',
                  cap?: { down: number; up: number },   // AI 給的效果一件事合計的上限（EVENTS 2.4）
                  floor?: string,                       // 下限是另一張量表的值（敵對值的下限）
                  adjust?(state, key, delta): number }) // 效果進來時的修正（區的倍率）
state.meters[kind][key]                                  // 沒寫的就是 start
{ op: 'meter', kind, key, delta } | { op: 'meter', kind, key, set }
meterOf(k, state, kind, key?): number
```

- 定義一種量表，同名的**效果** `{ kind, key?, amount }`（和現有的 `cash`、`cred` 一樣用 `amount`） 與**條件** `{ kind, key?, min?, max? }` 就自動註冊（上限照 0007 的三級：內建照寫、AI 照 `cap`）。`key` 省略時照 `keyed`：`district` 是現在這一區、`map` 是現在這張地圖的實例、`none` 是 `_`。
- M2 的量表：

| kind | 主人 | 照什麼記 | 範圍 | 出處 |
|---|---|---|---|---|
| `hostility`、`hostility_floor`、`favor` | security | 勢力 | 0～100 | FACTIONS 第 6 節、CORE_RULES 第 8 節 |
| `affinity` | npcs | 人 | −100～100 | NPC_SYSTEM 第 7 節 |
| `loyalty` | roster | 人 | 0～100 | NPC_SYSTEM 10.4 |
| `fame` | lewd | 區 | 0～100 | LEWD_SYSTEM 第 5 節 |
| `rep` | fixer | 單一 | 0～100 | CORE_RULES 第 8 節；同時註冊衍生數值 `rep_grade` |
| `insight` | scene | 單一 | 0 起，沒有上限 | LEWD_SYSTEM 第 10 節 |
| `alert` | explore | 地圖的實例 | 0～100 | COMMISSIONS 2.3、SITES 12.5 |

- 沒有人定義的種類，`meterOf` 回傳 0（那個功能這一局沒裝）；所以交易算折扣、互動算 DC 時直接問量表，不必知道誰管它。
- **規矩**：功能讀別人的數字只經由 `meterOf`、`k.stats`、`k.conditions`、內容（`k.content`）與核心的狀態（`party`、`actors`、`maps`、`money`）；寫只經由變更與效果。**不讀別的功能的 `state.ext`。** 人身上的狀況（有空、受傷、躲風頭、被捕、在忙）用核心的 `actor.conditions`，id 是共用的字彙：`busy`、`injured`、`lying_low`、`arrested`。
- 存檔升到第 3 版（多 `meters`；第 2 版的讀進來是空的表）。

### 四、事件導演是功能；事件視窗是通用的執行器（工單 M2-director、M2-event-run）

- 導演（`features/director`）在 `turn.end` 讀這一回合的 `report.triggers`，照 EVENTS 第 3 節擲；`daily`、`weekly` 聽 `time.passed`。發觸發點的功能只在自己的報告上寫 `triggers`，不知道導演存在。
- **事件視窗是活動 `event`**：`setup` 是 `{ event: id }` 或 `{ inline: 一件事件 }`。它管選項、看不看得到、檢定、四級結果、多段與版本（戰敗事件就是這個格式）。別的功能要玩家「在幾個選項裡選一個、可能擲一次骰」時都交給它：掃橋的怎麼過、俘虜的處置、雇主問要不要升階、戰敗事件。做完從 `activity.end` 拿到 `{ event, option, degree, flags }`。
- 結果分兩種：**改狀態的是效果**（`k.effects`，由管那塊狀態的功能註冊）；**開活動的是指示**（`fight`、`chain`、選項上的 `adult_scene`），執行器把它們變成 `launch`。沒有人登記 `scene` 這種活動時，`adult_scene` 當成沒有（退路）。
- 事件資料的效果一律寫物件 `{ kind, ... }`。EVENTS 第 7 節、DATA 第 4 節樣本裡的陣列寫法（`["cash", 300]`）是文件的簡寫，匯入時轉；引擎不收。

### 五、名冊的人進戰鬥；開打前帶進去的東西（工單 M2-core-battle、M2-roster、M2-abilities-m2）

- **隊伍就是核心的 `state.party`**（含主角最多 4 人）；探索開戰時我方照它排。同行（最多 2 位）不上場，是名冊自己的資料。
- **候補**：`k.battle.bench(owner, fn)` 回答「這一方現在叫得到誰」（每個人一筆 `{ id, ref, name, blocks }`）；`run.callIn(side, ref)` 把他排進後方的最前面、下一輪開頭補進最後面的空格（補位照 0013 C6），沒有空格回傳 `null`、不動狀態。名冊註冊候補（名冊上不在隊上、身上沒有 `busy`、`injured`、`lying_low`、`arrested` 的人）；技能的「增援」只呼叫 `callIn`，不知道名冊。
- **開戰設定的慣用鍵**（`BattleSetup.origin.ext`，誰發起誰填）：`by`、`commission`（0015 E3 的那個鍵）、`stage`、`face`、`pre: { spotted?, disguise? }`（開打前被識破了沒有）、`defeat_event`（副本自訂的戰敗事件）。
- `BattleSetup.edge?: 'ally' | 'foe'`：那一方每個人的先攻擲兩次取高（G7）。
- 敵人的來源多 `enemy_pick`（照勢力、等級、位階挑一個兵種），`enemy` 與 `enemy_pick` 的 `UnitRef` 可以寫 `attached` 蓋掉兵種自己的（詞條「獵犬」；工單 M2-enemy-encounter）。

### 六、時間與花費

| 做什麼 | 花多久 | 誰加 `time` |
|---|---|---|
| 在城市的街區走一格 | G8（暫定 1 分鐘，鏽帶 2） | world |
| 搭車 | 每站照 DISTRICTS 1.2.1 的表，加等車 | transit |
| 在委託的地圖上走、戰鬥、事件視窗、成人場景 | 0（0013 C5 照舊） | — |
| 副本的一個階段做完 | 120 分鐘（COMMISSIONS 6.2） | commission，在里程碑那一份 |
| 踩點一次 | 一個時段 | fixer |
| 喘口氣、睡一覺 | 60、480 分鐘（DOWNTIME 第 2 節） | rest |
| 打工一班 | 120／240／480 分鐘 | work |
| 換技能配置 | 衍生數值 `loadout_minutes`（G1） | abilities |

- **錢付不出來就是做不成**（原因一句），不會扣成負的；帳戶與現金哪一種照各功能的規則。
- **跨過時間點的事**都聽 `time.passed`，照固定的順序：帳單 10、敵對值的消退 12、名冊的每週 14、NPC 自己的日子 16、導演的 `daily` 與 `weekly` 20。核心給 `crossings(from, to, { every, offset })`（L1）算跨過了幾個點：每週是週一 06:00（DOWNTIME 5.1），每天是 08:00（EVENTS 3.1）。
- **休息做完**發核心的掛點 `rest.done`（`{ state, kind: 'breath' | 'sleep' | 'stage' }`，回傳變更）：「每次休息回滿」的東西聽它；副本裡階段之間的喘口氣也發（`stage`）。

### 七、M2 的接縫一覽

**報告的前綴**（`commit:<前綴>.<動詞>`）：`world`、`transit`、`grid`（探索，沿用）、`event`、`scan`、`scene`、`defeat`、`capture`、`commission`、`fixer`、`roster`、`favor`、`npc`、`security`、`trade`、`bill`、`rest`、`home`、`work`、`lewd`、`ability`（沿用）、`gear`（沿用）、`director`（導演的排隊與派角色）、`game`（開新遊戲）、`battle`（戰鬥的開始、結束與中止）、`rewind`（回退的保留）、`save`（讀檔與修復）。

**功能對功能的掛點**（一方問、多方答；宣告的那一方用 `declare module` 補型別，照 `defeat.options` 的做法）：

| 掛點 | 誰宣告、誰問 | 誰答 | 問什麼 |
|---|---|---|---|
| `activity.end`、`rest.done` | 核心 | 發起的功能；有「每次休息」的功能 | 第一、六節 |
| `director.cast` | director | npcs | 這個登場角色是誰（回傳角色的 id 與要先套的變更） |
| `scan.carried` | security | gear | 身上會被這一級掃到的東西 |
| `bill.collect`、`bill.settled` | bills | housing、roster（之後義體、店面……） | 這一週要收要付什麼；哪幾筆沒付成 |
| `defeat.options` | defeat（已經有） | abilities | 戰敗多出來的選項 |
| `fixer.offers` | fixer | 委託的生成（M2-commission-gen）；之後的特殊任務 | 這個中間人今天有哪些委託 |

**共用的資料慣例**（不 import，只認格式）：地圖實例的 `ext.guards`、`ext.reinforce`、`ext.origin`（探索讀，開地圖的人填）；`actor.ext.paths`（路數與階數，DATA 第 8 節）；`actor.ext.bridge`、`actor.ext.tendency`（DATA 第 8 節，lewd 管）。

## 後果

- 之後每一種新的玩法（子網、輿論戰、機甲整備的試車）是登記一種活動：副本的階段照 `face` 開它、等 `activity.end`，副本的程式不用改。M2 只登記現實面；沒有登記的面，玩家選不了，但輔助面照樣擲得了（那只是一次擲骰）。
- 外殼不再替每個功能加入口：介面的 store 直接呼叫功能匯出的純函式拿報告、交給 `Game.commit` 或 `Game.commitNarrated`；戰鬥原本的入口留著。
- 量表是核心的狀態，所以「這個勢力的敵對值」不必等 security 裝上才有地方放；但分段的效果、消退、區的倍率還是 security 的事。沒有人定義的量表種類，變更會被擋下（訊息寫出是哪一種）。
- 白名單的代價：副本裡能做的事要一個一個登記。清單在 M2-commission-run 的驗收條件裡守著。
- `snapshot.take` 讓快照變成資料的一部分，但文字要外殼給；只有核心、沒有外殼的測試由 testkit 給一個簡單的序列化函式。
- 事件執行器變成很多功能共用的東西：它的格式一動，掃橋、俘虜、戰敗、升階都要跟著看。格式以 M2-event-run 為準。
- 第八節被否決時要改的地方都只在一張工單的範圍裡；G1、G5、G6 動到的最多，先問。

## 實作補記（M2-core-battle，2026-11-23）

第五節的實作（`engine/src/core/battle/`；測試 `engine/tests/core/battle-m2.test.ts`）。設計沒有改，下面是工單沒寫、實作一定要有答案的幾處：

- **叫來還沒進場的人記在 `BattleState.called`**（單位 id，照叫的順序；沒有人在等時沒有這個欄位，舊存檔照讀）。他們同時在 `reserve` 最前面，平常的補位（`reinforce`）跳過他們、先補排在後面的人；下一輪開頭（`startRound`，`round.start` 之前）由 `admitCalled` 補進最後面的空格，補完或沒有空格（被別人佔了）都把這個欄位拿掉，留在後方的照平常補位。`battleProblems` 查 `called` 的每個 id 都在自己那一方的後方排著。叫來的人在後方被帶走（`setOut`）就不再等。
- **「沒有空格」的算法**：站在場上的 ＋ 後方等著的（含叫了還沒進場的）已經有四個就回傳 `null`。所以同一輪叫兩次、只有一個空格時第二次是 `null`（功能照 `fallback` 處理）。沒有空格時先回傳 `null`、不解 `ref`（來源查不到的錯只在有空格時才丟）。
- **進場的指標**：一輪開頭才進場的人，先攻排在最前面時就是這一輪第一個動（開頭誰都還沒動，輪到的指標不讓位）；中途補位的規矩不變（排在輪到的人前面時指標往後一格）。
- **叫來的單位**：id 是這一方下一個沒用過的 `a5`、`f5`……；行動點從上限開始（叫來時設好，`unit.ready` 裡的處理函式可以再改）；叫來的那一刻發一次 `unit.ready`（那一邊記的拍子不進紀錄，和開打時一樣）；進場那一拍沿用 `reinforce`，`data.called` 是 `true`；`call_in` 那一拍的 `data` 帶 `unit`、`side`、（有的話）`by`。`opts` 只有 `by`（誰叫的）與 `text`（換掉那一句）。
- **`view.bench` 的「已經在這一場裡」**：單位的 `actor` 等於候補的 `id`（或 `ref` 是 `{ from: 'actor', id }` 而 `id` 對得上）。倒下、退出、在後方等著、叫了還沒進場的人都算在裡面。不是角色的候補，來源拿到 `battle`、自己過濾。
- **`edge`**：只管開戰時上場的人，每個人的兩顆連著擲（不是先擲完一輪再補第二顆）；紀錄在「戰鬥開始」那一拍之後，每人一拍，`data` 是 `{ unit, edge, dice: [第一顆, 第二顆], initiative }`，沒有事件標籤。`edge` 不是 `ally` 或 `foe` 丟錯。
- **`distances`**：鍵是對面還在場上的單位（`f1`）與對面沒被擊落的掛著的東西（`o3`）的 id，值是核心的 `distance()`；敵方輪到時也算（`actions` 照舊是空的）；分出結果之後是空的。我方自己的掛著的東西不列（距離只算兩邊之間）。
- **搬動的程式**：開戰與叫人共用的「把 ref 解成單位」（`unitFromActor`、`resolveUnit`、`UnitRef`）搬到 `battle/units.ts`，避免 `setup.ts` 與 `run.ts` 互相 import；`setup.ts` 照舊匯出 `UnitRef` 與 `unitFromActor`，對外沒有變。

## 實作補記（M2-core-shell，2026-11-23）

第二、六節的實作（`engine/src/core/state/`、`core/util/time.ts`、`core/action/kindEntry.ts`、`shell/game.ts`、`shell/narrated.ts`；測試 `engine/tests/core/shell-m2.test.ts`、`engine/tests/whitebox/shell-m2.whitebox.test.ts`）。設計沒有改，下面是工單沒寫、實作一定要有答案的幾處：

- **「第一筆變更」怎麼知道**：`ChangeDef.validate`／`apply` 多一個選填的第三個參數 `at: { index, count }`（`applyAll` 給；直接呼叫、不給時不檢查）。`snapshot.take` 看 `index === 0`；試套用與真的套用都從 0 起算，`report.before` 掛鉤加的變更接在最後，擠不掉它。
- **序列化函式**：`StateKernel.serialize?`，Game 建好時注入 `snapshotText`（`shell/save.ts`，戰鬥開打前的快照同一份）。核心傳進去的是 `snapshots` 放空的淺拷貝，所以函式不必知道「快照裡不再包快照」；回傳不是非空的字串，整份報告不套。沒注入時變更不合法；testkit 的 `makeKernel`／`makeStateKernel`／`TEST_SERIALIZE` 給只有核心的測試用。
- **id 與流水號**：快照的 id 是 `s<流水號 + 1>`，並把 `seq.uid` 推到那個號碼（已經有人用的號碼跳過），這樣之後戰鬥開打前的快照（`s<uid + 1>`，不先推流水號）不會撞上。`replace` 在算 id 之後才拿掉舊的，所以換掉的那一份的號碼不會被重用。
- **帶 `rewind` 的報告在同一次提交裡回去**：外殼在 `commitAtomic` 裡、`launch` 開完之後，用 `restoreFrom`（`Game.rewind`、`rewindToKind` 共用的純函式）算出回去之後的狀態，整份換進那次提交的工作副本。所以「找不到快照、快照壞了、`rewind.keep` 的變更不合法」都是整步不成立（丟 `ActionBlocked`；任務鏈、走地圖回 `refused`），不會留下「報告提交了、人卻沒回去」。處理的入口是 `commit`、任務鏈的套用、`Game.launch`、`gridMove`、開局的 `setup`。回去之後清空回退步數、最新的鏈不能重試；回傳與通知的報告裡，這一步的報告標成被收回、最後多一份交代的 `rewind`。
- **報告的格式在提交時擋**：同一份報告不能同時帶 `launch` 與 `rewind`、`rewind` 要有字串的 `kind`（非空）與 `summary`，不然整份不收（`ChangeError`，在 `commitInto`，所以每一條提交的路都一樣）；一步裡有兩份報告帶 `rewind`（例：回合結束帶出來的又帶一個）丟一般的錯。`activity.end` 合併出來的 `launch` 與 `rewind` 同時有的，到提交時擋下：活動的主人組結束報告時要自己決定。
- **`rewindToKind` 的放行**：直接呼叫先問 `blockOf('rewind:<種類>')`（0016 第一節的 `doing`），被擋回傳原因；報告帶的 `rewind` 不另外問（那份報告的 `commit:<action>` 已經問過），所以「接受戰敗 → 委託失敗 → 回到入口」的那一份（丟掉開打前的快照、帶 `rewind`）照 `defeat` 的 `allows` 放行。
- **`commitNarrated` 永遠走鏈**：回傳 `ActResult`（`refused`／`paused`／`applied`）；AI 關著或設定關掉寫正文時，`narrate` 走退路（沒有正文），套用的草稿和 `commit` 一模一樣，只多鏈的記號（報告的 `chain`、一筆 `chain` 變更、`state.chains` 的一格與樓層），不另寫一條「不問 AI 就直接提交」的路，這樣重試、回退、`attach` 的規矩只有一套。`attach: true` 時不另留回退（鏈記著自己有沒有留，停在半路被丟下或被取消時只拿掉自己留的那一步）。鏈的代號（潤色的開關）固定是 `narrated`，不隨 `mode` 變。
- **成人路由**：草稿帶 `adult` 時，寫正文與潤色的請求帶 `adult: true`（`ChainDef.adult`、`TaskCtx.adult` 原本就有）。**成人路由的來源**（`AiSettings.adult` 的 `narrate_adult` 等）本來就還沒接到 `ProviderHub.resolve`，這張沒有碰；接上時只改 `resolve`，這條鏈不用動。
- **`crossings` 回傳 `GameTime[]`**，區間是（from, to]：同一刻是空的、出發在點上的不算（那一刻已經處理過）、走到點上的算。另有 `countCrossings`（O(1)，只要數量時用，帳單算「過了幾個週一」）、`dailyCrossings`、`weeklyCrossings`（週一照 `TimeRules.mondayRemainder`）。跨過超過 `MAX_CROSSINGS`（十萬）個丟錯。
- **`rest.done`**：型別在 `hooks.ts`，「跑掛點、收變更」是 `core/state/rest.ts` 的 `restDone(k, state, kind)`（和 `endActivity` 同一個做法：嚴格模式抓偷改、格式不對丟錯並寫出是誰）。
- **`actionKindToDef(entry, k, owner = 'actions')`**（`core/action/kindEntry.ts`）：`features/actions` 的 `toDef` 搬進核心並匯出，owner 是呼叫的功能給的；寫了 `owner` 的資料由那個功能用它轉成定義、再加上自己的東西。格式檢查（`check`）留在 `features/actions`。
- **格子（M2-world 追加）**：`facility` 做成核心的一種格子（走得上去、看得穿、標記 `F`，圖例 `F`），而不是 `defineCellKind`：標記格本來就是核心的靜態表（和 E、T、D、C、G、S、K、X、$、& 同一類），`Sheet`、`markersInLayout`、`sheetProblems` 都是不帶 kernel 的純函式，做成每個 kernel 各登記就得把 kernel 穿過它們；舊註解提到的 `defineCellKind` 從來沒有存在過，已改成「要新的種類加在 `CELL_TRAITS`」。`GridCtx` 多 `step`（從 1 起算）與 `last`（計畫的最後一格；路過的、被停下來沒走到終點的是 `false`；不是在走路時是 0 與 `true`），功能不必再自己用最短路推算。

## 實作補記（M2-core-meters，2026-11-23）

第三節的實作（`engine/src/core/state/meters.ts`、`core/rules/meters.ts`、`core/state/coreChanges.ts` 的 `meter`、`shell/save.ts`、`testkit/meters.ts`；測試 `engine/tests/core/meters.test.ts`；不變式第 94～98 條）。設計沒有改，ADR 都做得到。下面是工單沒寫、實作一定要有答案的幾處：

- **接線**：`k.meters`（`MeterRegistry`）掛在 L3 的 `StateKernel` 上，因為 `meter` 變更（L3）要問「這一種有沒有人定義、範圍多少」；L4 的 `createRulesKernel` 用 `meters.onDefine(...)` 接上自動註冊（`registerMeterRules`）。接線函式在定義存進登錄表**之前**跑，並且先確認效果與條件都沒撞名才註冊，所以撞名時什麼都沒留下。只有 L3 的核心也能定義量表、套 `meter` 變更，只是沒有同名的效果與條件。`registerCoreChanges(reg, serialize, meterEnv?)` 多第三個參數；不給時 `meter` 變更一律當沒有人定義。定義存的是複製（`cap` 也複製）。
- **保留字**：`all`、`any`、`not` 不能當量表的種類（條件的登錄表先處理這三個，量表的條件永遠走不到）。種類是 id 的格式。
- **不分對象的鍵固定是 `_`**：`keyed: 'none'` 的變更、效果、條件寫了別的鍵一律不合格（鍵只有一個，免得 `meterOf(k, s, kind)` 讀 `_`、別人寫到 `x` 而漏掉）。`map` 的鍵不查地圖實例存不存在（實例清掉之後留下的數字照留）。鍵不收 `__proto__`；讀寫都用 `hasOwn`，種類或鍵叫 `constructor` 也照常。
- **夾值的算法只有一份**（`nextMeterValue`）：`目標 = set ?? (現在的值 + delta)`，夾在 `[lo, hi]`，`hi = min(max, 安全整數)`，`lo = max(min, -安全整數, 下限那張同一個鍵的值)`，`lo` 比 `hi` 大以 `hi` 為準。所以**夾是「讓數字落在範圍內」，不是「只往動的方向夾」**：下限自己被抬高到比現在的值還高之後，下一次不管往上或往下動都會被抬到下限（下限自己往上不會立刻把這一種拉上去；要不要拉由管下限的功能決定，例：security 在加 `hostility_floor` 時一起寫一筆）。`floor` 指的那一種沒有人定義時當作沒有下限（不是 0：以免沒裝那個功能的一局，負值範圍的量表被卡在 0）。`min`、`max` 可以是 `-Infinity`、`Infinity`（體悟沒有上限），存進去的永遠是安全整數。
- **效果一筆進來的順序**：`adjust` → AI 的合計上限 → 範圍（見不變式第 97 條）。照 ADR 的「`adjust` 在夾值之前套」，**上限比的是修正之後的量**，AI 在冠冕區（×2）給 +8、`cap.up` 是 10，結果是 +10，不是 +16。為了讓「扣減」可以做到（`EffectBudget.resize` 只收一個新的量，修正又不能反推），被合計上限動過的效果與 `resolve` 吐出來的效果都帶 `adjusted: true`，意思是 `amount` 已經是修正過的量、不再修正第二次（`resolve` 輸出的效果再丟進 `resolve` 不會翻倍）。`adjust` 回傳的小數四捨五入成整數（.5 往離 0 遠的那邊：×0.5 的 +1 是 +1、−1 是 −1），不是有限的數字丟錯（那是定義它的功能的錯）。`adjust` 沒有鍵可以給時（現在不在區）不呼叫。
- **範圍在效果這一層就算成實際的量**：每一筆效果在 `clamp` 裡解出鍵、修正、夾進範圍，`amount` 寫的是實際動的量（`effects`、結果的那一行、變更的 `delta` 都是它），已經到頭的整筆拿掉；範圍的截斷**不給提醒**（到頭是常態，和 `hp` 補血不超過上限同一類），只有合計上限的扣減給提醒。這樣合計上限的「邊走邊算」（0007 的第二道）看到的也是實際的量，AI 的每一組實際淨變化不超過 `cap`（性質測試守著）。
- **省略的鍵什麼時候解**：分組用這一批開頭的狀態（現在這一區、現在的地圖）；真正套上去時用這一筆之前的狀態（同一批裡前面的效果搬了家，照新的區記）。已知限制：一批裡「搬家 → 省略鍵的效果 → 寫明鍵的同一種效果」這種寫法，分組可能和實際落的鍵不一致，合計上限會偏鬆；M2 的事件資料不會這樣寫，要寫的話把鍵寫明。不在任何一區（或不在任何一張地圖）而省略了鍵：這一筆沒有記下來，提醒用白話（「你現在不在任何一區……」）。
- **格式檢查**：效果的 `validate` 照 `item` 效果的做法查寫明的鍵（勢力、區在內容裡；人另外收存檔裡的角色），內容還沒載入時查不到就不合格；條件的 `validate` 沒有內容與狀態可看，只查格式（`faction`、`npc` 一定要寫 `key`、`none` 只能 `_`、`min`／`max` 是數字）。`amount` 是 0 合格，什麼都不產生。
- **`meterOf`**：`faction`、`npc` 沒寫 `key` 丟錯（呼叫的人的錯，訊息寫出量表）；`district`、`map` 現在不在區或不在地圖上時回傳 `start`；條件的 `test` 同一套。沒有人定義的種類回傳 0 不丟錯（工單）。
- **存檔**：遷移第 2 版升第 3 版補空表；`validateState` 查「種類 → 鍵（非空）→ 安全整數」的結構，**不查種類有沒有人定義、值在不在範圍**（沒有 kernel）。第 2 版存檔裡的快照文字也是第 2 版，`Game.rewind` 走 `unpackSave` 所以回得去（測試用的舊檔 `tests/fixtures/saves/v2-m1.json` 帶一份）。
- **報告卡**：`meter` 變更的一行是「量表的名字（勢力、人、區的名字）＋ 加減」，例：`好感（阿爾法） +5`、`街頭信譽 設為 20`；`delta` 是 0 不顯示。
- **testkit**：`testMeter(覆蓋?)`、`meterFeature(...定義)`、`METER_CONTENT`（假的兩個勢力與一位具名的人）；下游功能的測試用它們，不必等管那個量表的功能做完（dev/test-harness.md）。
- **改到的既有測試（一處）**：`tests/core/save.test.ts`「打包再讀回來，狀態一模一樣」裡 `SAVE_VERSION` 的斷言從 2 改成 3。

## 實作補記（M2-core-fix1，2026-11-23）

M2-npc-interact、M2-market、M2-roster 回報的核心缺口（工單 dev/work/M2-core-fix1.md）。設計沒有改，下面是有取捨的幾處：

- **算關係（relate）選「註冊任務、退路什麼都不記」**，不選「任務沒註冊就讓 `cast_present` 為假」：AI_TASKS 4.1 的 relate 是一個任務、退路是「一般的鏈不變」；任務鏈列也該看得到這一步。`relateEnabled` 固定為 `false`：AI 那一半（`submit_relationship`、共同記憶、關係描述）要等記憶有地方存（M2-npc-life 之後）再做，現在連 AI 開著也不發請求。自由行動與戰鬥結束兩條鏈都改了（`castOf`、`aiInput`、`aiEnabled`）。
- **報告帶行動的輸入**：`Report.args`（整份 `ActionInput`，型別搬到 L0 `types/report.ts`，`core/action/kinds.ts` 留一份再匯出）。只有 `buildActionReport` 寫，直接提交的報告沒有。npcs 與 roster 的文字標記拿掉，輸入不必再用 `interactInput`／`recruitInput` 組。
- **退路與參考範圍分開**：`ActionKindDef.hint` 是給 AI 的參考範圍（AI 的來源，照上限夾）、`fallback` 是規則表（內建的來源，不夾）。沒寫 `fallback` 的種類照舊用「參考範圍的一半」。**npcs 互動 AI 開著時的行為變了**：以前表的結果在 `report.before` 補進報告（AI 沒給的才補），現在只有算回報走退路時才用表；AI 開著而且交的合格時用 AI 的（照量表上限夾，所以偷竊大失敗的親密度 −20 在 AI 開著時是 −8）。表的結果同時放進 `hint`，AI 看得到基準。
- **算回報只照規則（`rewardByRules`）不選「把 `degree` 放進 `EffectCtx`」**：後者只保證 AI 交的 degree 對，AI 漏交整筆效果還是沒有；殺價這類結果完全由表決定的種類，AI 沒有東西可以補。`aiEnabled` 對 `reward` 回 `false`，步驟的狀態是 `fallback`，退路收到的 `degree` 是判定夾過之後的。
- **起手變更（`prelude`）**：算回報驗證用的狀態先套它，報告把它排在最前面。為什麼不放寬量表的鍵檢查：M2-npcs 規定還沒 meet 的生成人沒有量表可以動（`tests/features/M2-npcs.test.ts`），而第一次對路人做的互動要「認識他」和「加親密度」寫在同一份報告裡。
- **`item` 變更**：拿走（`qty < 0`）時 `data.uid` 是字串就只動那一疊；沒寫 `uid` 照舊（先拿沒有實例資料的）；得到（`qty > 0`）時 `data` 仍是新那一疊的實例資料。
