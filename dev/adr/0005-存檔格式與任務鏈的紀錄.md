# 0005 存檔格式、遷移的掛點與任務鏈的紀錄

- 日期：2026-11-21　狀態：採用

## 背景
MIGRATION 說存檔格式的版本從 1 開始。介面第四版已經有一種假存檔（`format: "cyberpunkpink-save"`，版本到 4），內容是假資料的形狀。任務鏈的細節要存在存檔裡、只留最近五樓（AI_TASKS 5.5 節）。

## 決定
1. 引擎的存檔用另一個格式標記 `cyberpunkpink-engine-save`，版本從 1 開始。介面的假存檔和引擎的存檔互相讀不了；介面換到引擎之後，舊的假存檔作廢（裡面本來就是假資料）。
2. 存檔是 `{ format, version, meta, state }`。`meta` 的摘要是主角的名字、出身、時間、地點（取代那邊的種族、職業、等級）。存檔的時刻由外面給，引擎不看時鐘。
3. 讀檔的順序固定：解析 → 認格式 → 照 `MIGRATIONS` 一版一版升上來（少一步就拒絕）→ 補缺的欄位、清存檔規則 → 結構檢查 → 年齡的底線（任何深度的 `age` 低於 18 整筆拒絕，不自動改）。
4. 讀檔修復（ElondiaRPG 寫在狀態層的 `load` 裡）改成 `save.loaded` 掛鉤：功能回傳變更，有才提交一份 `system` 報告。
5. 狀態的形狀一改就把 `STATE_VERSION` 加一、在 `MIGRATIONS` 加一步，並留一份舊版的存檔當回歸測試（`engine/tests/fixtures/saves/`）。
6. 任務鏈的細節（每一步的狀態、結果、每一次請求送出去的東西與原始的回應、錯誤）放在 `state.chains`，由一筆 `chain` 變更寫入；同一筆變更順手把五樓以前的細節清掉，只留 `{ id, floor, cleaned }`。
7. 每一次請求的開始與結束時間來自注入的時鐘（`GameOptions.now`）；測試給固定的時鐘，狀態才可重現。

## 後果
- 任務鏈的細節裡有完整的請求與回應，最近五樓會讓存檔變大（一樓大約幾 KB 到幾十 KB）。真的服務商接上之後量一次，太大就只存摘要、完整的另外放。
- 金鑰不在請求裡（由服務商那一層帶），所以不會進存檔。
- 正式環境的時鐘是真的時間，所以兩次遊玩的 `state.chains` 裡的時間會不同；其餘的狀態仍然可重現。
