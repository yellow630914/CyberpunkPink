# 0017 規則表可以被後載入的包取代；M2 收尾的幾個取捨

- 日期：2026-11-23　狀態：已實作（dev/work/M2-closeout.md；測試 engine/tests/core/M2-closeout-core.test.ts、engine/tests/features/M2-closeout.test.ts）；M2 修正批的補記在「M2 修正批的補記」一節（dev/work/M2-fix-review.md；測試 engine/tests/features/M2-fix-review.test.ts、engine/tests/core/M2-fix-review-core.test.ts）；M2 修 bug 批的補記（第 16～25 項）在最後一節（dev/work/M2-fix-bugs.md；測試 engine/tests/features/M2-fix-bugs.test.ts 與搬進主套件的 B016～B022、W014、W015）
- 延續 0016（活動、報告的代辦、量表；實作補記）、0005 以來的內容登錄表與覆蓋（快照 → 還原 → 套用）。

## 背景

M2 資料批次（M2-data-rules）把 18 張規則表接進 `CORE_PACK`（`transit_rule/default`、`event_scope/street`、各種 `*_rule`、設施種類……）。內容登錄表的規矩是「id 已經載入過就整批擋下」，所以任何後載入的包——介面的示意世界包、測試自帶的最小假資料、之後的模組——只要想放自己的一筆 `transit_rule/default`、自己的 `street` 事件範圍、自己的 `tuning_clinic` 設施種類，就載入失敗。介面那一批用了兩種繞法：示意包把核心包已經有的 id 過濾掉、測試把 id 改名（`street` → `street_t`）或整段拿掉（transit_rule 的公里數表、`tuning_clinic`）。這些繞法讓示意包與測試的資料不是它們想要的資料。

## 選項

1. **規則表種類宣告 `overridable`：後載入的包同 id 整筆取代前面的**。核心包先載入，其他包在後面；內容類（技能、物品、敵人、事件、勢力……）照舊重複就擋。
2. 規則表合併（欄位一個一個蓋）。
3. 所有種類都允許後載入的取代。
4. 不動登錄表，要改規則表一律走覆蓋（`applyOverlays` 的 `set`）。

## 決定

採用 1。

- `ContentKindDef.overridable?: boolean`；`ContentRegistry.isOverridable(kind)`。`load`／`loadPack` 對 overridable 的種類不查「已經載入過」，同一個 id 後來的取代前面的；`opts.replace` 照舊可以強制。**同一個包裡 id 重複照舊擋**（那是寫錯了，不是覆蓋）。
- 哪些種類是規則表由**註冊它的人**宣告（不是核心猜）：所有 `*_rule`（十八個：功能的十七個加核心的 `creation_rule`）、`event_scope`、`facility_type`、`shop_type`，核心的 `effect_cap`、`action_kind`、`battle_mode`、`damage_type`、`battle_status`、`weapon_class`。判準：這一種的每一筆是「數字或種類表」，功能讀它都是「資料蓋掉內建的預設」。內容類不是；要改內容類用覆蓋。測試 `第 10 項` 的最後兩條守著這張清單（新增 `*_rule` 忘了宣告會紅）。
- **整筆取代，不合併**。選項 2 的問題：欄位級的合併讓「這一局的規則表到底長什麼樣」要看三份資料疊起來；而每個功能讀規則表時本來就對沒寫的欄位用自己的預設（`genRules`、`billRules`、`interactRules`……），整筆取代加上功能的預設，效果和合併差不多，而且看一筆就知道全部。副作用：後載入的包只想改 `km` 時，`taxi_base` 等欄位會回到功能的預設（等於核心包資料的數字，因為資料等於預設）。
- 選項 3 拿掉了「兩個內容包不小心用了同一個 id」的保護（GAME_DESIGN 3 第 13 條），所以只開給規則表。選項 4 要改 `Game` 的組裝方式（覆蓋是 `applyOverlays` 在建好之後套的），而且測試與示意包要多寫一層，不如讓包的順序直接決定。
- `loadPack` 順便改成**整包不收**：格式與重複先全部檢查，再載入（以前一個種類載完才發現下一個種類重複，載到一半）。

## 後果

- 介面的示意包（ui/src/data/demo）放在核心包後面，直接帶自己的 `street`、`transit` 事件範圍與 `transit_rule`（公里數表）；測試用自己要的 id（`street`、`tuning_clinic`）。繞法都拿掉了。
- 後載入的包取代規則表之後，`checkRefs` 照舊檢查（取代的那一筆引用不到東西會在載入時被擋）。
- 規則表的取代是**這一局載入的內容**，不進存檔（存檔只有狀態；內容由包決定），和以前一樣。
- 新增規則表種類時，`defineKind` 要寫 `overridable: true`；`dev/test-harness.md` 不用改。

## M2 收尾的其他取捨（工單 M2-closeout 的實作補記）

1. **活動的放行帶條件，條件看得到「要開的是哪一段」**（第 1、2、5 項）。`k.activity.allow(kind, prefix, owner, when?)`，`when(state, doing, draft?, launch?)`。戰敗的 `chain:free_action` 只在事件視窗開著時放行（看活動 `event` 的 `active`，不看戰敗的階段：事件 chain 帶出第二件時階段是 `played` 但視窗開著）。`battle.start` 與 `event.start` 只放戰敗自己的流程開出來的：origin 是 `defeat`、或導演開的（`ext.caller` 是 `defeat`，或 chain 帶出來的那一件的 fight：它的 caller 記的是導演）。**不選「戰敗的放行清單直接加 `battle.start`」**：`Game.startBattle`、`Game.launch` 問的是同一個 `battle.start`，無條件放行等於等著選的期間玩家自己能開戰，丟掉 M1 審查 E1 擋住的那件事。為了讓條件分得出來，`blockOf`、`launchIn`、`Game.launch`、`Game.startBattle`、走路開戰都多帶 `launch`（一般的提交與任務鏈沒有）。
2. **導演問活動「現在能不能開事件」，不是自己數**（第 5 項）。`k.activity.permits(state, kind, doing, draft?, launch?)`：導演拿一個 origin 只有導演的 `event.start` 去問每一個進行中的活動，放行的（車上）不算「另一個活動」。戰敗等待中不放行導演開的（它的 `event.start` 是有條件的），所以戰敗期間導演照舊延後。這也是為什麼測試裡事件視窗的替身不能放行 `event.`（會被當成放行 `event.start`）：真的事件視窗只放 `commit:event.` 與 `chain:free_action`。
3. **劫囚（戰敗事件的 fight 結果）打完之後，被取代的那一場戰敗要清掉**（第 2 項）。新戰鬥開打時 `battleSnapshotChanges` 把「戰敗那一場開打前的快照」丟掉，三選一就不在了，`state.ext.defeat` 卻還在（介面會一直顯示戰敗面板）。defeat 在戰鬥結束掛點裡：不是打輸或投降，而且等待中的戰敗不是這一場，就把它清掉；打輸的話新的戰敗照舊取代舊的。**留下來的**：舊的戰敗沒有被「接受」過，所以發起那一場的人（副本）不會收到 `kind: defeat` 的 `activity.end`；劫囚的結果由那一場新戰鬥的 `activity.end`（`kind: battle`）交回。M2 的內容用不到，第一個用劫囚的內容要自己想清楚副本怎麼看。
4. **回到快照之後的接續報告**（第 3 項）。`restoreFrom` 改用 `commitReportAll`，回傳 `reports`（交代回到快照的、掛鉤接著提交的）。接續的報告若自己帶 `launch`，**不會**再開（回到快照之後狀態已經換了，那一步的 launch 早就跑完）；要在回去之後開活動是之後的事。
5. **街區地圖不要求遭遇點**（第 4 項）：`special_map` 的 `kind` 是 `block` 或 `bridge`（`STREET_MAP_KINDS`，和 world 的街區種類同名）就免；其他種類照舊每張至少 2 個（COMMISSION_MAPS 1.x 是副本模板的規定）。選「旗標」而不是看有沒有人登記：種類寫在地圖上，資料一看就知道。
6. **讀橋防護階：旗標 `manager`、`guard` 是 3**（第 8 項，NPC_SYSTEM 6.4）。設計書的 3 是「企業的主管、保全」，不是身分類（街坊／行者／職員）的一種，所以做成規則 `read.flag_tiers`（預設 `{ manager: 3, guard: 3 }`），和身分類的預設取高的；`shield:N` 旗標仍然優先。職員（店主、診所醫生）維持 2。
7. **遭遇組合與報酬範圍照設計書改**（第 8 項）：一般 4 點是四個雜兵（精英 2.5 湊不出剛好 4），首領戰 8 點是首領加三個雜兵，I 級沒有首領照 COMMISSION_TEMPLATES 的「兩個精英加兩個雜兵」（7 點）；報酬範圍是表的小型（×0.6）到大型（×1.8），規模在範圍裡的位置（`SCALE_POS`）沒動。債的利息 `debt_pay: { rouge: 'cash' }`（DOWNTIME 5.1），資料與程式的預設一起改，`bills` 讀規則時複製預設的 `debt_pay`（不是清空）。
8. **事件結束時臨時登場角色先不清，要留給接著開的活動**（第 9 項的連帶修正）。把俘虜帶走（事件的 `adult_scene`）時，臨時角色是那場成人場景的對象；npcs 在事件結束掃掉臨時角色，場景就開不起來（「找不到對象」）。導演在事件結束的 `activity.end` 的 `result.launch` 寫下接著開的活動種類，npcs 看到有 launch 就不掃，改成場景結束（`kind: scene`）或下一件事件結束時再掃。
9. **俘虜的審問選項只在副本裡放 `scout_reveal`**（第 9 項）：沒有 `origin.ext.commission` 就沒有「這件委託」可以揭開，而 `scout_reveal` 的格式檢查在手上沒有進行中的委託時不合格（abilities 的預備也靠這一條擋）。選「略過、不合格也不擋」會讓那一條保護失效，所以改在放它的地方。

## M2 修正批的補記（2026-11-23；dev/work/M2-fix-review.md，依據 dev/reviews/2026-11-23-M2.md 與使用者的裁決「都照建議」）

核心改了四處（`ReportRewind.fresh`、`turn.end` 的 `reports`、`ContentKindDef` 讓 `npc` 可覆寫、`compareText`／`compareNatural`），其餘在功能與資料。逐項：

1. **車上開打、開場景：這一趟車先結束，人在下一站**（必修 1；使用者定案）。選的是審查的做法二，不是做法一（`ride` 放行整組戰鬥、戰敗、場景的前綴）：做法一要讓車上的活動與戰鬥、戰敗、場景疊在一起，之後每多一種接在事件後面的活動都要回來改放行表，而且戰敗之後「接受結果」、回到階段開始這些動作的語意在車上沒有定義。
   - 交通功能（transit）聽事件視窗的 `activity.end`（導演在 `result.launch` 寫了接著要開的活動種類，見上面「M2 收尾的其他取捨」第 8 項）：手上有車票、而且那一種活動問 `k.activity.permits(state, 'ride', '<種類>.start')` 得到「不放行」時，回傳變更（`interruptRide`）：人放到這條線往前開的下一站（`nextIndex`；終點站沒有下一站就留在這一站；還在月台上也是這一站）、`transit.visit` 記一站、`transit.trip` 清掉、`ride` 自己的 `activity.end`（outcome `interrupted`，result 帶線、站、坐了幾站、付了多少）。這些變更併在事件收尾那一份報告裡，所以外殼接著開戰鬥或場景時，`ride` 已經不在，放行照原本的規則問。問的是 `permits` 而不是寫死 `battle`、`scene`：之後別的活動接在事件後面，只要車不放行就一樣處理。
   - **「下一站」的定義**：事件在上車後（`transit_wait`）、或坐到一站（`transit_stop`，`trip.at` 已經是那一站）跳出來，人都還沒下車；結束之後放到 `nextIndex(線, trip.at, trip.dir)`。沒坐完的票作廢：每一站的錢是坐那一站時才付，起跳是上車時付，所以沒有要補扣、也沒有要退的；不花時間（戰鬥與場景自己花）。
   - 事件視窗列選項時**不先問** launch 放不放行：現在每個選項都走得通。選項只開事件（chain）的不結束；選了不開活動的選項車照樣在（既有的 `M2-closeout` 測試）。
   - 句子不帶數字（寫正文時機制數字不進文字，見本節第 12 項）。
2. **副本放行表拿掉 `rewind:stage`、`rewind:entry`**（應修 1）。回到階段開始只在戰敗三選一裡（`Game.rewindToStage` 直接用 `rewindTo`，不問放行，本來就只在等著選的戰敗成立）；回到入口只走 `commission.retreat`（帶 `rewind` 的報告，核心提交時不另問 `rewind:` 的放行；0016 實作補記已經這樣寫）。`rewindToKind` 照放行表，沒改。既有測試裡拿 `rewindToKind('stage')` 當「回到階段開始」的改用 `Game.rewindTo(階段快照的 id)`（那一步就是戰敗三選一做的事），並多驗被擋。
3. **撤退與委託失敗回去之後骰子換一批**（應修 2；SERIES 第 6 節）。`ReportRewind` 多 `fresh?: boolean`；`restoreFrom` 在 `fresh` 時把亂數的**游標**設成 `max(快照的, 現在的) + 1`，**種子不動**。不換種子的原因：`state.rng.seed` 同時是這一局的世界（名冊的出場費與可靠度、NPC 生成與每天的行蹤、商品庫存、俘虜……都用 `hash32(seed, …)` 或 `cursor: 0`），換種子會讓撤退一次整個城市換一個樣子。游標只往前走，所以第二趟、第三趟的起點一定比前面用過的都大，三趟的第一擲不會撞到同一個亂數。`commission.retreat` 與戰敗被接受而算失敗（`onDefeatAccepted`）都帶 `fresh: true`（設計書沒明說失敗；失敗也是放棄整趟進度，一起定）；一般的回退（`Game.rewindTo`、回退一步、不給 `fresh` 的 `rewindToKind`）照舊固定骰值。`Game.rewindToKind(kind, summary, { fresh })` 多一個選項給之後的撤退類功能。
4. **副本內的事件**（應修 3）。
   - **同一件委託不重複**：範圍多 `unique_in_commission`（資料的 `commission` 範圍開）；導演在 `state.ext.director.in_commission` 記 `{ id: 副本的 id, events: [...] }`，id 取自進行中的活動 `commission`（導演本來就知道活動的 `kind`，不讀副本的 ext）；換一件委託就整份換掉（不累積舊的）；撤退、失敗回到進去之前時，導演的狀態整份回去，所以重來不算重複。
   - **壓力條漲過門檻多擲一次**：新觸發點 `pressure`（範圍表 `{ stage: 0.3, pressure: 0.15 }`），範圍的 `events_as: { pressure: 'stage' }` 讓事件照 EVENTS 3.1 寫的 `stage` 就收（也收直接寫 `pressure` 的）。副本在 `report.after` 看到警戒（量表 `alert`，那一段地圖的）第一次到 `pressure_at`（規則，預設 60；用 `>=`，和評價的 `rating_alert` 同一個門檻寫法）就接一份 `commission.pressure`，帶 `pressure` 觸發點，並在 run 記 `pressured`（一個階段只發一次；階段之間清掉；開地圖時警戒就在門檻以上的，`chooseBranch` 直接記成發過，不算「跨過」；戰鬥中不發，打完那一份報告再發）。**警戒整趟累計**（下一階段從上一階段的值起算），所以實際上一趟多半只跨過一次。
   - **`turn.end` 的 payload 多 `reports`**：行動自己那一份加上 `report.after` 掛鉤接著提交的報告（唯讀的複製）。導演從 `reports` 收集觸發點，不再只看 `reports[0]`。這是核心的一個加欄位，現有的處理函式不受影響。選這個而不是「報告提交前 `report.before` 替它加觸發點」：警戒漲過門檻是看了這份報告的變更之後才知道的事。
   - **還沒做**：EVENTS 3.3 範圍冷卻欄「每個階段最多一件」（現在階段開始的 30% 與壓力條的 15% 各自擲，同一階段可以出兩件，兩件不同）。要做的話，導演要知道「現在第幾階段」（`where` 帶階段數、範圍記每個階段的件數）；等有內容需要時再補。
5. **成人路由接到服務商**（應修 4）。`ProviderHub.resolve(settings, task, { adult })`、`sourceNameFor(..., { adult })`：`adult` 時先看 `settings.adult[ADULT_SOURCE_KEY[task] ?? task]`，沒指定就回到一般的來源（PROMPTS 2.13：成人來源預設和一般的相同）。`ADULT_SOURCE_KEY`：`narrate`、`polish` → `narrate_adult`；`scene_gate`、`scene_turn`、`scene_talk` → `scene`；`sex_record`、`sink`、`tendency` → `aftercare`；`npc_news` → `npc_news_adult`；`image` → `image_adult`。`runTask` 把 `ctx.adult` 傳進去。備用模型（`fb`）本來就沒有接到 `resolve`，成人來源「先不設備用」的規定自然成立。
