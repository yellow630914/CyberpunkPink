# AI 任務與工具（初稿）

> 上層：[IMPLEMENTATION](IMPLEMENTATION.md) 第 2 節。依據：ElondiaRPG 的 Agent 模式計畫（那邊的 `docs/plan/roadmap/AGENT_MODE_PLAN.md`，狀態是還沒開始）與它現有 AI 呼叫的盤點（[scan/02-ai](scan/02-ai.md)）。
> 這是規格的初稿。數值上限都是暫定，動工後依實際的費用與穩定度調。

## 1. 原則

沿用 ElondiaRPG 的計畫，加上這個專案的兩條：

1. **引擎是唯一的真相。** 報告直接放進請求；AI 不改狀態。
2. **一件事一個任務。** 每個任務有自己的提示詞檔、模型設定、輸入、輸出、驗證與退路，可以單獨測試、單獨換模型。
3. **工具調用取代事後解析。**
   - 查詢工具是唯讀的，取代「把所有資料先塞進提示詞」。
   - 寫入工具要經程式驗證才生效，取代「正文後面附一段讓程式讀」與「整份 JSON」。
   - 不合法的呼叫回傳錯誤，讓 AI 當場改，不再默默夾值。
4. **寫入先排隊，正文結束後在同一個回合套用**，所以回退會一起回退。那邊的性經歷記錄目前不在回退範圍內，這邊從一開始就避免。
5. **編排是程式，不是 AI。** 這一回合叫哪幾個任務、順序、並行，由引擎照任務鏈決定（1.1 節）。Agent 模式開著時，AI 可以提議多做一步，但仍由程式驗證與排程（1.2 節）。
6. **每個任務都有不用 AI 的退路。** AI 關著、逾時、格式錯，程式照規則結算。逾時與取消對所有任務一致（那邊只有判定有）。
7. **工具調用不支援時要能退回。** 有些服務商不支援工具調用，這時退回「結構化輸出」：單次請求，一份固定格式的結果，用同一套驗證。連線測試要多測一項工具調用。
8. **一次請求的工具呼叫有上限**（暫定 6 次），超過就用已經有的結果結束。
9. **成人內容的分流由引擎決定。** 走哪個模型、附不附成人規則、開不開成人的寫入工具，看狀態，不看 AI。

### 1.1 任務鏈

**每一種流程都有一條明確的任務鏈**（不只成人場景）：依序叫哪幾個任務、每一步能用哪些工具、每一步失敗時怎麼走。鏈寫在資料裡（預定 `data/ai/chains.json`），不散在程式各處。

| 流程 | 任務鏈 |
|---|---|
| 自由行動 | 擲骰（程式）→ **judge** →（程式結算）→ **narrate** |
| 一般的行動（移動、交易、休息……） | （程式結算）→ **narrate** |
| 戰鬥的一回合 | （程式結算全部）→ **narrate**（可以幾回合合併寫一次） |
| 可能進成人場景的行動 | judge 或程式結算 → **scene_gate** → 進：建立場景；不進：**narrate** |
| 成人場景 | 每回合：玩家行動 → **scene_turn**（對方選行動，附一句動作或台詞）→ 程式結算；結束：**scene_settle** → **narrate**（整場寫一次） |
| 談判、對峙 | **npc_act**（給選項）→ 玩家選 → 程式檢定 → **narrate** |
| 輿論戰的一回合 | 玩家出牌 → 程式結算 → **pr_move**（對手）→ 程式結算 → **narrate** |
| 接委託 | **commission_gen** → 程式驗證並建立副本 → **narrate**（中間人怎麼開口） |
| 進店、見到新的人 | **flavor_shop**／**flavor_roster**（背景執行，不擋玩家） |
| 訂做零件 | **design_part** → 程式夾值 → **narrate** |

- 鏈上的每一步都是 2.1～2.3 節的任務；每個任務有自己的退路，所以鏈的任何一步失敗，都能照規則走完。
- 判定與敘事之間一定隔著程式的結算：AI 不能在同一步既決定結果又寫結果。

### 1.2 兩種模式：Agent 關與開

| | **Agent 模式關**（預設，最穩定） | **Agent 模式開**（更有活力） |
|---|---|---|
| 誰決定叫哪些任務 | **程式**，照 1.1 節的任務鏈，一步不多、一步不少 | 程式照鏈走；另外允許 AI 在鏈的固定位置**提議**多做一步 |
| AI 拿資料的方式 | 程式把需要的資料先放進請求（不靠工具調用） | 查詢工具：AI 自己決定要查什麼 |
| AI 交結果的方式 | 每個任務一份固定格式的結果（結構化輸出），程式驗證 | 寫入工具：逐筆驗證，不合法的當場回錯誤讓 AI 改 |
| AI 能不能主動觸發系統 | 不能 | **能，但只能透過寫入工具提議**：留伏筆（`add_hook`）、讓一個 NPC 找上門、提議一件事件（`propose_event`）、提議進成人場景、提議一件委託 |
| AI 能不能生成事件 | 不能；事件只來自事件導演的資料 | 能：`propose_event` 交出一件符合事件格式的事件，程式驗證後交給事件導演排進佇列（[EVENTS](../systems/EVENTS.md)）。**以單發事件為主**；對系列只是調味或指引，不寫系列成員的旗標（[SERIES](../systems/SERIES.md) 第 7 節） |
| 花費與延遲 | 固定、可預估 | 較高、有上限（每回合的工具呼叫次數、每天 AI 生成事件的件數） |
| 不支援工具調用的服務商 | 完全可用 | 自動退回關的做法 |

- **關的時候系統要是最穩定的**：所有流程都能只靠程式判斷任務鏈跑完；這也是 AI 完全關掉時的退路往上一層。開發與測試以這個模式為基準。
- **開的時候是在同一條鏈上加東西，不是換一套系統**：任務、驗證、上限都是同一份；多的只有查詢工具、逐筆的寫入工具，以及幾個「提議」類的工具。
- AI 主動提議的東西一律經過和資料驅動的內容**同一套驗證與上限**：事件導演的每回合上限與優先序、內容篩選、封閉的效果清單。AI 提議的事件不能繞過這些。
- 每一種「主動」各有開關（設定 → AI），可以只開查詢、不開生成事件。

## 2. 任務

### 2.1 每回合的任務

| 任務 | 什麼時候 | 輸出 | 可用的工具 | 模型 | 退路 |
|---|---|---|---|---|---|
| **judge**（判定） | 自由行動擲骰之後 | 終結工具 `submit_judgment` | 查詢全部；寫入：`grant_reward`、`update_relationship`、`set_flag`、`add_hook`、`add_rumor`、`apply_condition`、`recruit`、`meet_npc`、`design_part` | 中 | 照規則結算，或讓玩家重試 |
| **narrate**（敘事） | 報告產生之後 | 串流的正文 | 查詢：地圖、人物、關係、記憶、世界書；寫入：`update_relationship`、`record_sex`（只在成人路由）、`add_hook` | 大 | 不寫正文，只顯示報告的摘要 |
| **scene_gate**（成人場景的進入點） | 互動、誘惑、事件、蜜罐、戰敗之後，引擎判斷「可能」時 | `submit_scene_gate`：進或不進、這一場的性質與目的 | 查詢：人物、關係、傾向 | 小 | 不進 |
| **scene_turn**（成人場景的對方行動） | 回合制成人場景，輪到對方 | `submit_scene_action`：從可用的行動裡選一個 | 查詢：人物、傾向、這一場的狀態 | 小 | 依對方的性格與傾向用權重抽 |
| **scene_settle**（成人場景的結算） | 場景結束 | 寫入：`record_sex`、`adjust_sink`（沉溺 −4～+4）、`add_tendency` | 查詢：這一場的經過 | 小 | 程式照契合與動作結算 |

- 判定與敘事分開，所以擲骰與後果不會被文字帶著走。
- 續寫、依玩家意圖重寫併入 narrate，用模式參數區分；這兩種模式不開寫入工具。
- 親密關係對沉溺的影響「由 AI 判定性質、程式只夾數值」（[CORE_RULES](../systems/CORE_RULES.md) 4.3 節），放在 scene_settle。

### 2.2 遊戲中按需的任務

| 任務 | 什麼時候 | 輸出 | 退路 |
|---|---|---|---|
| **npc_act**（NPC 在對話、交涉時選行動） | 談判開始、對峙 | `submit_options`：一組選項 | 用模板的選項 |
| **pr_move**（對手公關在輿論戰出牌） | 輿論戰輪到對手 | `submit_pr_move`：從可用的牌選一張，附理由 | 依權重抽 |
| **commission_gen**（委託的內容） | 中間人或流竄 AI 發委託時 | `submit_commission`：目標、主面與輔助面、里程碑、未知清單 | 用模板生成 |
| **flavor_roster**（新 NPC 的細節） | 第一次見到生成的 NPC | `submit_roster` | 用模板 |
| **flavor_shop**（店裡今天的貨與優惠） | 每間店每天第一次進 | `propose_deal`，每筆單獨驗證 | 用模板 |
| **npc_news**（NPC 的近況） | NPC 的日常有變化或重逢 | `submit_news` | 不寫 |
| **design_part**（訂做零件） | 向社團或 NPC 訂做 | 寫入工具 `design_part`，程式夾在那個等級的範圍內 | 照模板給 |

成人向的批次要有自己的模型設定，不借用別的任務的（那邊的 NPC 近況借用了性經歷的設定）。

### 2.3 工具類的任務

| 任務 | 什麼時候 | 說明 |
|---|---|---|
| **image_prompt**、**storyboard** | 生成立繪、日誌插圖 | 照搬；分鏡改用 `submit_storyboard`，不再寬鬆解析 |
| **quest_designer**（特殊任務生成） | 世界編輯器 | 照搬，改用 `search_catalog` 查目錄、`validate_quest` 取代「把錯誤交回去再送一次」 |
| **connection_test** | 設定頁 | 加一項「工具調用測試」 |

### 2.4 不是 AI 的

| 事 | 誰做 |
|---|---|
| 記憶與摘要 | 程式照規則合併（那邊也是） |
| 外觀描述、主角的稱呼 | 程式 |
| 編排 | 程式 |

## 3. 工具

### 3.1 查詢（唯讀）

| 工具 | 參數 | 回傳 |
|---|---|---|
| `get_here` | — | 這一格附近的文字地圖、在場的人、可去的地方。解決那邊「AI 編出地圖上找不到的人和地點」的問題 |
| `get_character` | `id`、`detail: brief\|full` | 主角或 NPC：外觀、狀態、義體、傾向（成人路由才含） |
| `get_relationship` | `npc_id`、`memories ≤ 6` | 關係、好感、共同記憶 |
| `search_memories` | `participants?`、`location?`、`limit ≤ 6` | 相關的記憶 |
| `get_inventory` | `category?` | 行囊與裝備 |
| `get_faction` | `faction_id` | 這個勢力對主角的好感與熱度、文化分支 |
| `get_commission` | `id?` | 進行中的委託：目標、三個面的指標、里程碑 |
| `get_net` | — | 在內海時：這個子網的節點、追蹤度、控制節點 |
| `get_sex_record` | `id` | 性經歷（只在成人路由） |
| `search_lore` | `query`、`limit` | 世界書的關鍵字比對；常駐的條目仍放在固定的那一段 |

### 3.2 寫入（程式驗證）

| 工具 | 參數（摘要） | 驗證 |
|---|---|---|
| `submit_judgment`（終結） | 成功程度、用的屬性與基本功、DC、理由、轉折、摘要、要花的時間 | 封閉清單與上限，沿用那邊判定的清理；**要先於其他依賴成功程度的寫入** |
| `grant_reward` | 信用點、物品、零件、**取代或加上**、理由 | 依成功程度與委託的報酬上限 |
| `update_relationship` | `npc_id`、好感變化、一句話的關係描述、理由 | 單次上限；描述仍是提議，玩家確認 |
| `adjust_faction` | `faction_id`、好感或熱度的變化、理由 | 單次上限 |
| `set_flag` | `key`、`value` | 只能寫 `ai:` 開頭的旗標 |
| `add_hook` | 誰（在場或認識的人，或「新的人」由程式產生）、在哪（只能是 `get_here` 給的地點）、何時、一句話 | 一區同時最多一則；有期限。掛在系列上時只能放在標了 `ai_hook` 的成員，性質是**指引**：指向已經存在、條件已成立的內容（[SERIES](../systems/SERIES.md) 第 7 節） |
| `add_rumor` | 標題、內容、地點 | |
| `propose_event` | 一件符合事件格式的事件：範圍、選項、檢定、效果（只在 Agent 模式開著時） | 事件格式的驗證、封閉的效果清單、內容篩選；交給事件導演排程，受每回合與每天的上限 |
| `apply_condition` | 生命、感載的變化 | 單次上限 |
| `recruit` | `npc_id` | 要成功程度夠 |
| `meet_npc` | 外觀、性格、背景（名字由程式產生） | |
| `design_part` | 零件類型、材質、等級、屬性、特性 | 夾在那個等級允許的範圍內（[CRAFTING](../gear/CRAFTING.md) 第 11 節） |
| `record_sex` | 參與者、類型、次數、一句話、第一次、偏好 | 參與者只能是在場的人；沿用那邊的驗證 |
| `adjust_sink` | `delta`（−4～+4）、性質、理由 | 只在 scene_settle |
| `add_tendency` | 傾向標籤、量 | 只能是這一場碰到的 |
| `submit_*` | 各批次任務的結果 | 各自的格式 |

## 4. 服務商這一層要加的

照搬那邊的服務商（Anthropic、OpenAI、相容 OpenAI 的服務、Gemini、Vertex）、用量統計與快取，再加：

- 多輪訊息的型別，以及「有工具的對話迴圈」。
- 串流改成事件流：文字、工具呼叫、工具結果、結束。
- 各家的工具格式對應；Anthropic 的思考區塊在多輪之間要保留。
- 偵測是否支援工具調用，不支援就退回結構化輸出。
- 所有任務一致的逾時、取消、用量統計。
- 工具定義放在固定的前段，讓快取命中。

## 5. 試做的順序

照那邊計畫的建議，先證明迴圈能跑：

1. 先做 judge 與 narrate，**只開 Anthropic 一家**。
2. 第一個查詢工具：`get_here`。
3. 第一個寫入工具：`record_sex`（取代另外一次請求，效果最明顯）。
4. 穩定後換掉關係更新與判定的效果，再加其他任務。
