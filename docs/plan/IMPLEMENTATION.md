## 2. Agent 模式：把 AI 的工作拆成任務

**原則不變**：引擎是唯一的真相；AI 不改狀態，只回傳結構化的結果，由程式檢查、夾在允許的範圍內才寫入。Agent 模式改的是「一次呼叫做很多事」這件事——改成**一件事一個任務**，每個任務有自己的輸入、輸出格式、可用的資料與失敗時的退路。

### 2.1 每個任務要寫明的東西

| 欄位 | 內容 |
|---|---|
| 名稱與目的 | 這個任務回答哪一個問題 |
| 觸發 | 引擎在什麼時候叫它 |
| 輸入 | 給它哪些資料（報告的哪一段、哪些世界書條目、哪些角色卡）。只給需要的 |
| 輸出 | 固定的結構（列舉值、數值範圍、文字欄位）。程式照結構驗證 |
| 夾限 | 程式對輸出做的限制（例：沉溺每場 −4～+4） |
| 退路 | AI 關著、逾時或格式錯的時候，程式怎麼自己決定 |
| 可不可以並行 | 能和哪些任務同時跑 |
| 模型的等級 | 這個任務需要多強的模型（判定類可以用小的，敘事用大的） |

### 2.2 預計的任務種類（初稿，掃描後會調整）

| 類別 | 任務 | 文件裡已經出現的地方 |
|---|---|---|
| **判定** | 自由行動的成功程度與後果 | [CORE_RULES](../systems/CORE_RULES.md) 第 3 節 |
| | 成人場景的進入點：這一刻該不該進 | [LEWD_SYSTEM](../systems/LEWD_SYSTEM.md) 第 3 節 |
| | 親密關係的性質（決定沉溺往哪邊動） | [CORE_RULES](../systems/CORE_RULES.md) 4.3 節 |
| | 這一場碰到了哪些傾向 | [LEWD_SYSTEM](../systems/LEWD_SYSTEM.md) 1.1 節 |
| **扮演** | NPC 在對話、交涉、成人場景裡選哪個行動 | [LEWD_SYSTEM](../systems/LEWD_SYSTEM.md) 第 3 節 |
| | 對手公關在輿論戰裡出什麼牌 | [OPINION](../systems/OPINION.md) |
| **生成** | 委託的內容（目標、里程碑、未知清單） | [COMMISSIONS](../systems/COMMISSIONS.md) |
| | 街頭事件、訂做的零件、NPC 的細節 | [CRAFTING](../gear/CRAFTING.md) 第 11 節 |
| **敘事** | 把報告寫成文字（戰鬥、探索、對話、成人場景各一種） | [GAME_DESIGN](../GAME_DESIGN.md) |
| **記憶** | 摘要一段經過、更新 NPC 對主角的印象、挑出要帶進下一次的世界書條目 | — |
| **編排** | 決定這一回合要叫哪幾個任務、順序與並行 | 這一層是程式，不是 AI |

- 一次玩家行動通常是：**判定 →（引擎結算）→ 敘事**，旁邊並行跑記憶類。判定與敘事分開，是為了讓擲骰與後果不被文字帶著走。
- 編排由程式做，不交給 AI 自己決定要叫誰。這樣每回合的花費與延遲可以預估。
- 每個任務的提示詞各自一份檔案，可以單獨測試、單獨換模型。
- 成人內容的分流照舊：要不要走成人向的敘事，由引擎的狀態決定，不由 AI 決定。

### 2.3 掃描後的修正

ElondiaRPG 那邊的 Agent 模式計畫（還沒開始）重點是**工具調用**，不只是拆任務：查詢工具取代把資料塞進提示詞，寫入工具取代事後解析，寫入在正文之後套用、可以回退。這邊以那份為準，任務與工具的定稿在 [AI_TASKS](AI_TASKS.md)。上面的表是動工前的初稿，和 [AI_TASKS](AI_TASKS.md) 不一致時以後者為準。

## 3. 程式掃描：預計怎麼做

**範圍**：ElondiaRPG 的 `src/engine/`、`src/narrator/`、`src/stores/`、`src/components/`、`data/rules/`、測試。只讀，不改那邊的任何東西。

**要回答的問題**

| # | 問題 | 產出 |
|---|---|---|
| 1 | 每個模組依賴誰、被誰依賴 | 依賴圖；找出可以單獨搬的與纏在一起的 |
| 2 | 哪些是**共用的管道**（不帶奇幻的假設，兩邊都能用） | 共用管道清單：報告、存檔、回退、效果模板、主動行動、格子地圖、事件、旗標、AI 呼叫、世界書注入…… |
| 3 | 哪些地方把奇幻的假設寫死了（等級、職業、魔力、種族） | 每一處的位置，搬的時候要改 |
| 4 | 所有呼叫 AI 的地方：誰叫的、給了什麼、要回什麼、怎麼驗證 | AI 呼叫清單，對照第 2 節拆成任務 |
| 5 | 重複的邏輯：同一件事寫了兩次以上的 | 重複清單 |
| 6 | 沒有人用的程式、資料欄位、元件 | 死碼清單 |
| 7 | 測試蓋到哪裡 | 每個要搬的模組有沒有測試可以一起帶走 |
| 8 | 介面元件：哪些只是版面、哪些把規則寫在元件裡 | 元件分類；規則要移回引擎的那些 |

**做法**

1. 先用工具跑出依賴圖與行數（機械的部分）。
2. 依 [MIGRATION](MIGRATION.md) 的 A～P 組，一組一組讀，回答上面八個問題。
3. 每組的結果先各自寫下來，最後合成兩份文件（下面）。
4. 掃描期間發現 [MIGRATION](MIGRATION.md) 的判斷有誤（例如以為可以照搬、其實纏得很深），就回頭修正那份清單與 [ROADMAP](ROADMAP.md) 的階段。

**產出放在哪**

| 文件 | 內容 | 給誰 |
|---|---|---|
| `plan/CODESCAN.md` | 依賴圖、共用管道清單、奇幻假設的位置、AI 呼叫清單 | 這個專案搬模組時用 |
| `plan/AI_TASKS.md` | 第 2 節的任務表定稿：每個任務的輸入、輸出、夾限、退路 | 這個專案；也是 Agent 模式的規格 |
| `plan/ELONDIA_CLEANUP.md` | 給 ElondiaRPG 的減熵清單（第 4 節） | 另一邊 |

## 4. 給 ElondiaRPG 的減熵清單

**在這個專案把共用的部分搬完、整理好之後才交**——那時候才知道哪些整理是真的行得通的。

清單預計的格式，每一條：

| 欄位 | 內容 |
|---|---|
| 位置 | 哪個模組、哪個函式 |
| 問題 | 重複、死碼、規則寫在元件裡、假設寫死、兩個模組互相依賴…… |
| 建議 | 怎麼改；這個專案是怎麼整理的（附對照的檔案） |
| 風險 | 改了可能影響哪些地方；有沒有測試保護 |
| 大小 | 小、中、大 |
| 優先 | 依「省下多少複雜度 ÷ 風險」排 |

另外附：

- **共用管道的對照表**：同一條管道，這邊整理後的樣子與那邊現在的樣子，方便直接照著改。
- **Agent 模式的任務規格**：`AI_TASKS.md` 裡不帶賽博龐克設定的那一部分，那邊可以直接用。

這份清單只是建議。ElondiaRPG 那邊要不要改、什麼時候改，由你決定；這個專案不會去動那個儲存庫。
