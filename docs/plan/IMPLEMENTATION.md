## 2. Agent 模式：把 AI 的工作拆成任務

**原則不變**：引擎是唯一的真相；AI 不改狀態，只回傳結構化的結果，由程式檢查、夾在允許的範圍內才寫入。Agent 模式改的是「一次呼叫做很多事」這件事——改成**一件事一個任務**，每個任務有自己的輸入、輸出格式、可用的資料與失敗時的退路。

### 2.1 每個任務要寫明的東西

| 欄位 | 內容 |
|---|---|
| 名稱與目的 | 這個任務回答哪一個問題 |
| 觸發 | 引擎在什麼時候叫它 |
| 輸入 | 給它哪些資料（報告的哪一段、哪些世界書條目、哪些角色卡）。只給需要的 |
| 輸出 | 固定的結構（列舉值、數值範圍、文字欄位）。程式照結構驗證 |
| 夾限 | 程式對輸出做的限制（例：沉溺每場 −4～+4） |
| 退路 | AI 關著、逾時或格式錯的時候，程式怎麼自己決定 |
| 可不可以並行 | 能和哪些任務同時跑 |
| 模型的等級 | 這個任務需要多強的模型（判定類可以用小的，敘事用大的） |

### 2.2 做法

- 一次玩家行動通常是：**判定 →（引擎結算）→ 敘事**，旁邊並行跑記憶類。判定與敘事分開，是為了讓擲骰與後果不被文字帶著走。
- 記憶與摘要由程式照規則合併，不算 AI 任務（[AI_TASKS](AI_TASKS.md) 2.4 節）。
- 編排由程式做，不交給 AI 自己決定要叫誰。這樣每回合的花費與延遲可以預估。
- 每個任務的提示詞各自一份檔案，可以單獨測試、單獨換模型。
- 成人內容的分流照舊：要不要走成人向的敘事，由引擎的狀態決定，不由 AI 決定。
- 重點是**工具調用**，不只是拆任務：查詢工具取代把資料塞進提示詞，寫入工具取代事後解析，寫入在正文之後套用、可以回退。任務與工具的規格在 [AI_TASKS](AI_TASKS.md)。

## 3. 程式掃描

**範圍**：ElondiaRPG 的 `src/engine/`、`src/narrator/`、`src/stores/`、`src/components/`、`data/rules/`、測試。只讀，不改那邊的任何東西。

結論在 [CODESCAN](CODESCAN.md)：依賴圖、共用管道、奇幻假設的位置、每個系統的判定、新專案的分層。AI 呼叫的盤點併進 [AI_TASKS](AI_TASKS.md)。給 ElondiaRPG 的減熵清單之後另寫成 `plan/ELONDIA_CLEANUP.md`（第 4 節）。

## 4. 給 ElondiaRPG 的減熵清單

**在這個專案把共用的部分搬完、整理好之後才交**——那時候才知道哪些整理是真的行得通的。

清單預計的格式，每一條：

| 欄位 | 內容 |
|---|---|
| 位置 | 哪個模組、哪個函式 |
| 問題 | 重複、死碼、規則寫在元件裡、假設寫死、兩個模組互相依賴…… |
| 建議 | 怎麼改；這個專案是怎麼整理的（附對照的檔案） |
| 風險 | 改了可能影響哪些地方；有沒有測試保護 |
| 大小 | 小、中、大 |
| 優先 | 依「省下多少複雜度 ÷ 風險」排 |

另外附：

- **共用管道的對照表**：同一條管道，這邊整理後的樣子與那邊現在的樣子，方便直接照著改。
- **Agent 模式的任務規格**：`AI_TASKS.md` 裡不帶賽博龐克設定的那一部分，那邊可以直接用。

這份清單只是建議。ElondiaRPG 那邊要不要改、什麼時候改，由你決定；這個專案不會去動那個儲存庫。

## 5. 順序

| 步 | 做什麼 | 說明 |
|---|---|---|
| 1 | **遊戲引擎核心** | 照 [CODESCAN](CODESCAN.md) 第 3、4 節的分層與順序、[MIGRATION](MIGRATION.md) 的清單搬或重寫；AI 呼叫一開始就照任務拆。三個戰場的畫面與規則以 `mockups/` 的三個 Demo 當實作的參考 |
| 2 | **世界編輯器**（接口） | 內容進引擎的接口與編輯器 |
| 3 | **潤色** | 配合平衡後的數字、去 AI 味；在純文件上做 |
| 4 | **匯入** | 把潤色過的內容匯進引擎 |

- **平衡**在另一個工作階段跑，必須在引擎核心與世界編輯器完成之前做完。
- 給 ElondiaRPG 的減熵清單（第 4 節）在共用管道搬完、整理好之後交第一版，之後補。
- 細的排程在 [PLAN](PLAN.md)。
